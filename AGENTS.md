# Somnio

A browser-based mini-MMORPG with a 3D world. A TypeScript gameplay server, an admin CLI, and a Three.js browser client in one npm workspace, plus a localhost-only web map editor under `packages/web/`.

## Tech Stack

- Node 24 (`.nvmrc`), TypeScript run directly through Node's type stripping — nothing is compiled, so every package's `exports` point at `.ts` sources
- Hono + `@hono/node-server` for HTTP, `ws` for the two WebSocket routes, Kysely over `pg` for Postgres, `argon2` for password hashing, pino for logging, commander for the CLI
- Vitest for every suite; `@testcontainers/postgresql` for the integration projects
- Three.js + Vite for the browser client

## Package graph

```
packages/protocol   # message catalog, the sector view, `{tag, payload}` codec — imports nothing
packages/core       # game models (sector, character, inventory, world clock), the world of
                    # spaces and doors, geometry, collision and ground height, the rules of
                    # combat, lucidity, and speech, the .somnio-sector codec, the model
                    # registry, the core catalog — depends on protocol
packages/data       # Postgres schema + its migrations, repositories, Argon2id hashing,
                    # SHA-256 session-token digests (unsalted so the digest column is directly
                    # searchable — safe because the token is a 256-bit CSPRNG value), the
                    # name policy — depends on core
packages/server     # gameplay/admin handlers, the per-connection actor, per-space
                    # simulation, world router, services, the HTTP/WS server, boot —
                    # depends on protocol + core + data
packages/cli        # admin CLI: command tree, transport, output rendering, its catalog —
                    # depends on protocol + core
packages/web        # browser client + web map editor — depends on protocol + core
```

The graph is enforced twice: each package's `package.json` declares exactly its `@somnio/*` dependencies (which is what `npm ci --workspace` links in the images), and the root ESLint config forbids any other `@somnio/*` import under `packages/<name>/src/**`. Test files may reach outside it through `devDependencies`.

Module rules for the non-web packages: relative imports carry the `.ts` extension, `import type` for types, no `enum`, no constructor parameter properties (`erasableSyntaxOnly`), `with { type: 'json' }` for JSON imports. The web package keeps its Vite conventions.

**Type stripping and `node_modules`.** Node never strips types under a real `node_modules` directory; it works here only because npm links the workspace packages as symlinks, which resolve back into `packages/*`. Never install them with `--install-links`, and the server image copies the whole install tree for the same reason.

## Build & Test

```
npm ci
npm test                 # every package's unit project; never starts a container
npm run test:integration # data + server integration projects over testcontainers Postgres (Docker or Podman)
npm run typecheck        # tsc --noEmit over both tsconfigs (web, and the rest)
npm run lint             # eslint, including the package-graph rule
npm run format:check     # prettier
npm run knip             # unused files, exports, and dependencies
npm run build            # the browser client's production bundle, then the editor-exclusion assertion
npm run dev              # gameplay server (dev defaults) and the Vite client together; needs the somnio-pg container
```

`npm test` runs every project listed in the root `vitest.config.ts`; the integration projects join only under `SOMNIO_INTEGRATION=1`, which `test:integration` sets. Under rootless Podman set `TESTCONTAINERS_RYUK_DISABLED=true`.

`npm test` starts no container but does bind loopback ports, so a sandbox that denies `listen` fails these files with `EPERM`: the server's live-socket suites (`packages/server/test/live/`, `admin-auth-gate`, `socket-close`) and the CLI's `transport.test.ts` start the gameplay server or a bare `ws` server, and `packages/web/test/editor-fs.test.ts` runs the editor's file middleware behind an HTTP server.

The server: `SOMNIO_DEV_DEFAULTS=1 node packages/server/src/main.ts` (env in the Deployment section; the `/somnio-server` skill has the dev-container recipe). The CLI: `node packages/cli/src/main.ts <verb>`. Both run the sources directly, so a change takes effect on the next start.

## Browser client (`packages/web/`)

A Three.js client that speaks the wire protocol through the shared `@somnio/protocol` package.

```
npm run dev --workspace packages/web      # Vite on :17669, proxying /ws to the local server on :17662
npm run editor --workspace packages/web   # Vite with the editor entry + sector file API (see "Web map editor")
npm run conformance                       # wire conformance against a LIVE server (SOMNIO_CONFORMANCE_URL)
```

### What holds the client and server together

The protocol and core packages are shared code, so the two sides cannot disagree about a message shape. They also run the same movement rule (`packages/core/src/collision.ts`) over the same sectors and the same registry geometry. Two suites guard the parts that are not shared:

- **Golden frames** (`packages/protocol/fixtures/golden-frames.json`) are compared as canonicalized JSON (object keys sorted) by `golden-frames.test.ts`. This is the check that catches a payload **property rename** — the round-trip suites encode and decode with the same renamed property and stay green. Re-record deliberately with `SOMNIO_RECORD_GOLDEN_FRAMES=1 npx vitest run --project protocol`.
- **Wire conformance** (`packages/web/test/conformance/`) drives the real TypeScript encoder and transport into a real server. Its outbound case is what proves application frames ship as **text**; everything else in that file passes while the transport sends binary. The over-cap frame case accepts either close code in `[1009, 1006]`: the client is still writing a ~1 MiB payload when the server refuses it, so whether the close frame arrives before the reset is transport timing.

### Browser-only decisions

- **Session tokens.** A browser page needs a refresh to survive, so the server issues a resumable token on `Login.requestSessionToken` and accepts `redeemSession`/`revokeSession`/`revokeOtherSessions`. Issuance is **request-gated** on that optional field: a client that never asks receives no `sessionToken` frame. `revokeOtherSessions` is the game menu's Log Out Other Browsers. It deletes the account's other rows and spares the token the connection redeemed or was issued, the one this browser holds. Its answer, `otherSessionsRevoked`, counts the unexpired rows it ended. Unlike `revokeSession`, it leaves this browser logged in and in the world. A login or a session redeem reports `otherSessions {count}`, the account's other unexpired rows, and the menu offers the action only while that count is above 0. One account has one live connection, so no other browser can add a row while this one plays. The count can therefore only fall until the next login or redeem.
- **DOM UI over WebGL.** Panels and overlays are real elements, so password managers work and `agent-browser snapshot` sees them. `packages/web/src/ui/chrome.css` draws the Kenney 9-slice chrome with `border-image-slice: 36` against an 18px border — the slice is unitless *image pixels*.
- **The orthographic camera's `scale` is a vertical HALF-height**, so the Three.js mapping is `top/bottom = ±scale`, `left/right = ±scale × aspect`. The usual `frustumSize / 2` idiom halves it again and renders the whole world at 2x. The game's default is 7, 14 m shown top to bottom (`ORTHO_RIG` in `packages/web/src/scene/cameraRig.ts`). The player zooms by the wheel or a pinch between 0.78 and 1.4 times that (`PLAYER_ZOOM`), a half-height from 5 m to about 9 m. The editor keeps a zoom range of its own (`EDITOR_ZOOM`).
- **Resize holds the vertical world extent constant.** A gameplay contract, not a rendering detail: a bigger window magnifies rather than reveals. Name plaques and speech bubbles are sized in metres too, but never drawn smaller than 1.2 CSS pixels per pixel of their art (`OVERLAY_MIN_SCREEN_PIXELS` in `overlayArt.ts`), so their text stays readable on a small window or a phone.
- **The ground is painted, not textured.** Each sector's ground is one plane whose shader draws every floor material from a procedural recipe (`packages/web/src/scene/groundMaterials.ts`, the one list of floor-material ids) by two weight textures. `groundField.ts` computes those weights from the sector's background, its touching outdoor neighbours' backgrounds (blended over 5 m in noisy patches), and the marks of all of them. One field takes tens of milliseconds, so `groundRasterizer.ts` runs it in a module worker, and inline where there is no worker or the worker fails. Two touching sectors of one texel size (every sector up to 81.92 m across) compute identical weights wherever both rasterize, so their seam cannot show: every input is keyed to space position, marks paint in one order (sector name, then index), and a sector's raster carries a gutter past its edge. The scene keeps drawing a sector's previous field until the next arrives, and paints the player's own sector on the spot before revealing a new space.
- **A press on the play field selects, walks, or steers.** A mouse, a finger, and a pen take one path, the primary button only. The scene picks by shape what is drawn under the pointer: first an entity's body (`WorldScene.entityAt`, a capsule from feet to head as wide as the body is drawn, nearest the camera first, its radius at least 0.6 m on a coarse pointer), then the player's own body, then the ground (`WorldScene.groundPointAt`, which meets the top of a walk surface before the floor beyond it). A press on a body never walks the player. A press on the player's own body stops them. A press on the ground keeps the target. Up within 180 ms and 12 px of where it landed (`HOLD_TO_STEER_MS`, `TAP_SLOP_PX`), it is a tap, which walks to where it landed. Held longer or moved further, it steers toward the ground under the pointer, and on coming up walks on to where it came up. A second pointer down makes it a pinch, which zooms and walks nowhere until every pointer is up.
- **One target.** A press on a body (`GameplaySession.pressEntity`) makes it the target, which a ring marks, and so does a press on a dreamer's name in the Players window. An NPC within speaking distance is also asked to go on, which opens a master's or the shopkeeper's panel. A press on the player's own frame, or on their own name in the Players window, makes them their own target, and the target frame reads their health from their own `energy`. The ✕ on the target frame clears the target. Escape takes one thing away at a time: the open chat, then a finger's menu sheet, then the newest open window, then the target, and only then does it open the game menu.
- **A mouse's right button locks the gaze.** A right press on a body, the same pick as a left press, makes it the target and has the player face it whatever the cursor does (`GameplaySession.toggleGazeOn`), so a left press then only walks. The target's ring is a gold reticle meanwhile, and the target frame's accessible name says so. A second right press on the target, or one on the ground, ends the lock and keeps the target, and one on the player's own body does nothing. The lock also ends with the target: cleared, changed by a left press on another body, out of view, driven off, or left behind in another space. A pen, a finger, and a coarse pointer have no right press.
- **Slot 1 acts on the target.** It is one toggle, the first slot of the HUD's belt (the big button under the right thumb on a finger's layout) or the 1 key. What it does there, and when it goes on and off, is `engageAction` in `packages/core/src/combat.ts` and the `engage` rules (see "Acting"), applied alike on both sides. The button is named and drawn for that action, Raise where Mend meets a fallen dreamer. It is lit while on. At anything else it is greyed out and keeps its last look, so a Healer holding the Moonstone, which does not swing, finds it greyed out at a nightmare. The client never walks the player toward the target, and slows its own player when a `blow` names them as the attacker, since the server chooses the moment of each swing.
- **The HUD** (`packages/web/src/ui/hud.ts`, styled by `hud.css`, which the editor does not load). The player's own frame sits top left: their portrait in a ring of their condition, their people's sigil on a badge at its foot, their name, and their people and role. The people comes from each `enterSpace`, so a resume straight into the world draws it too. The target frame sits top centre with the target's portrait, and the world clock top right, as `☾ 22:40` or `☀ 14:05` with the sector's place name (`placeNames.ts`). The client runs the clock on from `enterSpace` (`ConnectionController.worldSecondsAt`), and the sun is up from 6 to 22, as the world's light has it (`sunIsUp` in `dayNightSun.ts`). The belt sits bottom centre: a Health globe and a Spirit globe filled by the exact pools, a Balance arc across its top that turns orange under a Winded tag, slot 1, slots 2–6 held empty for abilities, Run at its end, and one line saying what the player studies and how far toward the next rank. Players, Bag, and Settings sit beside the Spirit globe. The first two open windows, several at once with the newest on top, each closed by its ✕; Settings is the game menu. Speech bubbles keep clear of every HUD part that shows (`GameHUD.occluders`), the faded chat excepted. On a mouse, in a window too narrow or too short for it, the HUD shrinks evenly (`GameHUD.setViewport`): the frames, the clock, and the belt scale toward the edges they stand at, so each stays whole and none overlaps another. A window keeps its width and ends above the menu.
- **The chat is a pane, not a panel.** It lies bottom left as text. Its lines fade 8 s after the last one arrived or the pointer left them, and come back while the pointer rests where they lie. Enter, while the world has the keyboard and no control takes Enter itself, opens it with the field focused. Enter there sends the line, or with nothing typed sends nothing, and either way closes the chat and hands the keyboard back, so Shift runs again. Escape closes it too.
- **The HUD's art is the chrome's.** Everything is white line art over flat dark fills, at the 9-slice borders' 2px weight, with no gloss, glow, or gradient. A globe is a dark well in a 2px ring with a bracket arc outside it at the top and the bottom, filled flat from the bottom with a lighter line at the surface. A slot, a menu button, and a phone's round button show that they are on by a tinted plate and a second line just inside the edge, in the colour of what they do. The glyphs (`hudIcons.ts`) are Kenney's white CC0 icons from the pack's `UI/`, used as CSS masks over the control's ink (`.hud-glyph`), so one icon takes any colour. Where Kenney has nothing that fits, a glyph is drawn in `hudIcons.ts` as white SVG in the same weight: the chat balloon, the Moonstone, and the four people sigils.
- **A portrait is the body itself.** Each frame's circle is left open in its plate, and after the world renders, `WorldScene.drawPortraits` draws the in-world body again in it on the same canvas, through an orthographic camera three-quarters in front of the body as it is turned (`packages/web/src/scene/portraits.ts`). It is not a clone, so it shows every clip the body plays in the same frame, and a fallen body is looked down on at its head bone. Its camera draws one layer, which the subject's model and the scene's lights carry and nothing else does, so no plaque, ring, prop, or ground shows, and the body's materials keep the programs the world compiled for them. A square with the circle cut out at the front of the depth range and a backdrop disc at the back clip the body to the circle, so the world drawn under the frame stays outside it. The backdrop is a light grey-violet behind the head, darkening to its rim, so a dark body such as a Ghost reads as a silhouette against it. The pass leaves the shadow maps and the scene's matrices as the world's render left them, and lifts only the hemisphere fill's intensity to a floor while it draws. The circles' rects are read once a frame, with the panels', so a frame lays the page out once.
- **A coarse pointer gets a landscape layout** (`.hud--coarse` in `hud.css`, chosen once from `(pointer: coarse)` at startup). One strip runs along the top: the player's frame, with a small portrait and small Health and Spirit bars in place of the globes, then the target frame, then the clock and a ≡ that opens a sheet with Players, Bag, Settings, and the study line. Slot 1 is a big button under the right thumb, with slots 2–6 on an arc round it and Run at the arc's end. Balance is a thin bar at the bottom between the chat icon and Run. The chat hides behind an icon bottom left, its newest lines peeking above it and fading as on a mouse, and opens as a panel with a ✕. A window opens one at a time, as a panel down the right edge. Closing the chat blurs its field on every device, so a phone's keyboard shows only while the chat is open. The edges keep clear of the safe-area insets. An upright phone (`UPRIGHT_PHONE_QUERY`: a coarse pointer, portrait, at most 600 px wide) is covered by a card asking to turn it sideways, which goes once it turns. That card is the only hold a browser tab has on orientation, since a manifest's orientation binds only an installed app. The canvas takes no browser touch gesture and no long-press menu.
- **A panel keeps its elements while its inputs are unchanged.** `AppShell.render` runs on every state change, and a recovering pool sends several `energy` frames a second. A panel that replaced its children on each of them would swap a button between press and release, or a row between the two clicks of a double-click, and the click would be lost. Each panel remembers what it last rendered from and returns early on the same inputs, pinned by element-identity tests.
- **A speech command covers its own line only.** A line starting with `/w` (`/whisper`, `/flüstern`) is whispered and one starting with `/y` (`/yell`, `/schreien`) is yelled. `/s` (`/say`, `/sagen`) says a line plainly, as a line with no command is said.
- **Speech bubbles keep apart.** The scene lays every bubble out at once each frame (`packages/web/src/scene/bubbleLayout.ts`). The shell paints them on a 2D canvas over the game canvas and under the panels, so nothing in the world hides a line. A speaker whose head is on screen gets the bubble at the nearest free spot round that head, leaning toward above, clear of every head, every other bubble, and every visible panel. It keeps the spot it has while that stays free and settles back over the head once that is free. With no free spot left it stays by the head and overlaps; it is never pinned. Its tail ends on the head where it is drawn, a fallen body's where it lies. Every tail is drawn under every bubble, so a tail may pass behind another bubble but never across its text. A bubble is as wide as its text, up to a full line.
- **Speech the player cannot see is placed where it comes from.** A voice through a door hangs its bubble by that door: outdoors over the doorway on the building, and in a room in the dark just past the wall it comes through. Where that spot is off screen, where a room's is taken, and for a speaker whose head is off screen, the bubble is pinned on the line from the player toward the voice, as near the screen's edge as is free. With nothing free on that line, it overlaps as near the edge as no panel covers. That line is taken on screen, because the camera's yaw turns ground bearings. A pinned voice's chat line names one of eight compass directions. The pin and the direction are both judged from where the bodies stand as the line arrives. A hidden tab draws no frames, so its bodies would otherwise stand where the last frame left them. A bubble fades with `clarity`, a whisper's outline is dashed, and a yell's is yellow and spiky.
- **Plaques stay behind the world.** Where plaques overlap, the target's draws on top, then the more hurt over the less hurt, the player's own, and the rest nearer the camera over further. Only the target's plaque shows through bodies and props. A hale nightmare shows its name only while it is the target. Nothing is hovered, on any pointer, so a touch screen and a mouse show the same plaques.
- **A master's panel is not an overlay.** It opens on a press at the master and closes on walking out of speaking distance, and the input gate stays open under it, so the player keeps moving. The shopkeeper's panel is the same panel. It locks its buttons from a trade until half a second after its answer, so a double click trades once. A refused trade gets no answer, so the lock also gives way after 1.5 s.
- **Rooms are lit by their own flames.** In a room, a model with a registry `light` (a candle, a lamp, a torch, the hearth) carries a halo at its flame and a warm pool of light. Outdoors the same models draw unlit, with no halo. The pools come from a fixed set of 8 point lights (`PROP_LIGHT_POOL_SIZE` in `packages/web/src/scene/propLights.ts`), so the scene's light count, and with it every shader program, never changes from space to space. A ninth flame would draw its halo and light nothing, so a room holds at most 8 such models, and `room-lights.test.ts` holds the committed rooms to it. A room's key light is dim enough to let the flames show. A shadowed spot light lets the hour's light in through the room's first door (`doorLightState` in `dayNightSun.ts`): warm by day, faint and cool at night. The pools and the door's light follow the space on screen, so during a held swap they change in the same frame as its geometry. A flame's halo and pool flicker together, held steady under reduced motion.
- **One-shot clips have no fallback.** The fall, a swing, and a flinch (`ONE_SHOT_CLIPS` in `packages/web/src/scene/animation.ts`) are events, not poses, so a model without the clip keeps its looping pose.
- **Before login the world plays a reel.** `packages/web/src/splash/` stages the committed sectors with scripted dreamers, NPCs, and nightmares. The sectors are compiled into the bundle through `@somnio/core/fixtures/sectors/*`, so the reel needs no server. It plays a fixed run of 6–8 s shots joined by a dip to dark, and reduced motion holds the first shot with a still camera. A fixture edit can put a wall in a scripted path or move an edge into a framing, and `splash-reel.test.ts` fails on either. It requires every path to be legal and every outdoor framing to stay on ground. Each figure a shot is about must be on screen whole, its name plate included, and clear of the card's column, which also covers the wordmark because the wordmark is narrower than the card. In a shot that follows a subject, every figure must be framed that way too once it stands. On a window too narrow to hold those figures beside the card, the camera of a followed shot pulls back, up to the scene's widest scale. A 50% veil dims the world. The wordmark sits in a band that ends above the tallest pre-login card, so it never moves between cards. The reel stops when a session attaches, and the scene's held swap carries its last frame into the game.
- **The pre-login screens give way when the player's own body is placed**, a little after `enterSpace`. Only then do the veil and the wordmark go and the HUD appear, and a later join never brings the splash back. When the session ends the HUD hides and closes its chat and windows. Until then a failed login says why on the login card, and a silent resume's retry says so under the wordmark.
- **A login lands on the character card**, one of the pre-login screens, with the reel still playing behind it. New Dreamer opens a form for a name and a people, and Delete asks first in an overlay of its own. The card locks its buttons from a request until its answer, so a double click sends one request. Every card request is answered, so unlike the shopkeeper's panel the lock needs no fallback timeout. Log Out on the card revokes a remembered session and returns to the login card, as Leave Game does from the world. A resume of an account with a dreamer played goes straight into the world. The player's own name comes from their own `entity` frame.
- **`window.somnio`** is a read-only debug surface (dev always, production via `?debug=1`). It reports positions in metres in the space's coordinates, each entity's `condition`, and the player's own state. `screenPoint(entityId)` is where on the page an entity is drawn, a fallen body where it lies, for a click aimed at it, and `groundScreenPoint(x, z)` is where a point of the space is drawn on the ground, for a tap aimed there. They are reads, not commands: a recipe drives the client with real pointer events at those points. The `/somnio-web` skill lists every call and covers driving the client with `agent-browser`.

### Web map editor

The map editor is a second Vite entry point (`packages/web/editor.html` + `packages/web/src/editor/**`) that authors `.somnio-sector` files — a development tool, not a shipped surface:

- **Dev-only by construction.** `editor.html` is deliberately never added to `build.rollupOptions.input`, so `vite build`'s default single input (`index.html`) keeps it out of `dist/` and therefore out of the image. `npm run build` machine-enforces this: `packages/web/scripts/assertEditorExcluded.mjs` runs after `vite build`, inside the image build too, and asserts `dist/editor.html` is absent and no editor marker (`__editor/sectors`, `somnioEditor`, `somnio-editor-root`) reaches `dist/bundle` or `dist/index.html`.
- **File I/O is a dev-server middleware** (`packages/web/vite.editorFs.ts`): a `configureServer`-only plugin serving `/__editor/sectors` (GET list, GET/PUT per percent-encoded stem, no DELETE), inert unless `SOMNIO_EDITOR_SECTORS_DIR` is set (the `editor` npm script sets it, defaulting to the repo-root `sectors/` staging directory; a dev server with `SOMNIO_SECTORS_DIR` pointed there plays what is being authored, and finished sectors are copied into `packages/core/fixtures/sectors`, the world the server image ships and the splash reel stages), loopback-only and same-origin-gated regardless of `--host`, path-contained against the realpath'd root, and atomic on write.
- **The sector codec** (`packages/core/src/sectorFile.ts`) is pinned byte-for-byte by the committed fixtures, each of which reads and writes back identical, so an authored save never rewrites unrelated bytes of a sector the server loads. The writer runs its output through the reader before returning it, so the editor cannot save a file the server would refuse.
- **The overlay shows what blocks.** The authoring overlay draws each placement's registry colliders along with walk surfaces, ledges, door triggers, and arrival points. A door is the one record kind without a tool: it is added from its placement's inspector at one of the model's anchors.
- **The document is judged as `buildWorld` would judge it.** Every other sector in the directory is loaded on open, and `documentIssues` (`packages/web/src/editor/surroundings.ts`) runs `buildWorld` over all of them. The overlay marks each reported record in red, and `window.somnioEditor.issues()` lists them. What the rules need of named sectors (the inn's spawn, the Healer trial's `NorthWood`) is checked by the server alone, in `ruleSectorIssues`.
- **Neighbours are drawn read-only.** For an outdoor document the outdoor sectors touching it are drawn at their origins, so roads, walls, and tree lines can meet across a border.
- **Record labels are DOM elements** over the canvas, so `agent-browser snapshot` sees them.
- **English-only.** The editor renders literal English and never imports `@/i18n`, keeping `RENDERED_KEYS` and the catalog tests untouched.
- **It shares the client's chrome.** The editor loads `packages/web/src/ui/chrome.css` and builds its corner panels with the `packages/web/src/ui/dom.ts` helpers (`floating`, `floatingStack`, the panel and button builders). A change to either reaches the editor too, so check it there as well as in the game.
- The `/somnio-editor` skill covers serving and driving the editor with `agent-browser` (`window.somnioEditor` is its debug surface).

### Web asset pack

The browser reads glTF. `somnio-assets` carries `Web/Models/*.glb`, published by its `Pipeline/build-web-models.sh`, and `Web/Branding/` (the favicon, home-screen icon, and wordmark), written by its `Branding/scripts/export_web.py`. The panel textures and the HUD's icons live in that repo's root `UI/`. `Scripts/bundle-web-assets.sh` composes the served root from the three:

```
SOMNIO_ASSET_SOURCE=/path/to/somnio-assets \
SOMNIO_WEB_ASSET_DEST=packages/web/dist/assets \
  Scripts/bundle-web-assets.sh
```

The destination differs by consumer, and getting it wrong fails silently. `packages/web/dist/assets` is for the image build, where nginx serves `dist/`; the **dev server needs `packages/web/public/assets`**. Vite serves `packages/web/public` and `packages/web/`, never `dist/`, so a pack written to `dist` leaves every model and texture 404ing with a placeholder world and no error. `packages/web/public/assets` is gitignored and excluded from the Docker context, so a populated dev pack never leaks into an image.

`UI/` and `Web/Branding/` are required, because neither the chrome nor the brand has a fallback. Models only warn. The brand is served at `/assets/Branding/`. The script and CI's pack check both check its four files by name, and every `UI/` file the client loads (`UI_FILES` in the script), because a directory check passes a partial export. A missing icon would draw its control blank. `packages/web/test/ui-pack.test.ts` holds that list to the `/assets/UI/` URLs under `packages/web/src` and to CI's check. An icon added to the HUD therefore needs its file in `somnio-assets` first: that repo is pushed before the somnio commit that names the file, or CI's pack check fails.

The script additionally verifies **external resource sidecars**, both `buffers[]` and `images[]`, which is the whole surface glTF 2.0 declares external files on. Today's pack is entirely self-contained binary GLB, so the check finds nothing. It exists because a JSON glTF can point at a sibling `.bin` or `.png`, which three.js resolves relative to the model URL, so a pipeline change that started emitting one would serve a 404 for the model's geometry or its texture.

The served layout is `/assets/...` for the pack and `/bundle/...` for hashed build output (`build.assetsDir: 'bundle'`). They must not share a directory — the client references the pack by absolute URL.

Prop models (the registry's `objectModels` stems, empty `expectedClips`) are **placement-normalized before export**: local origin at the ground-footprint center, long horizontal axis along X. The runtime adds no per-object scale and puts each clone's origin at its placement's `x`/`z`, turned by `yaw`. Collision never measures a loaded model: it comes from the registry's `footprint` and `colliders`, so an un-normalized prop draws shifted or mis-sized against what it blocks. The pipeline's footprint gate holds each written model's ground bounds to its registry `footprint`. The pipeline's sizing modes and authoring conventions live in that repo's `CLAUDE.md`.

### Hosting

`packages/web/Dockerfile` builds `ghcr.io/tobihagemann/somnio-web` from a **repository-root** context (the workspace symlinks resolve through the root `node_modules`, and the asset pack is at `assets/`). It requires `--build-arg BUILD_VERSION` like the server image, and greps the bundle for the marked stamp `somnio-web <version>` to prove the version was injected — see `packages/web/src/buildInfo.ts` for why the stamp interpolates the define directly rather than reusing the exported constant.

There are no releases, version numbers, tags, or changelog. The `publish` job in `ci.yml` builds both images from every commit on `main` that passes the other four jobs and pushes them as `ghcr.io/tobihagemann/somnio-server` and `somnio-web`, each tagged `sha-<short>` and `latest`. `BUILD_VERSION` is that short sha, so the admin `version` verb and the `somnio-web <version>` stamp name the exact commit a container runs. The deployment runs `latest` for both images and redeploys whenever any service in its stack changes, so any green commit on `main` can go live at any moment: a change that breaks the wire must bump `helloVersion` in the same commit (registry geometry counts, see "Wire protocol"), and the committed sector fixtures are the live world.

The static image does **not** proxy `/ws`; whatever fronts it performs the split (the `proxy` service in `docker-compose.example.yml` locally, Traefik in production), which is what lets the client's origin-relative `wss://<host>/ws` resolve with no dev-only branch.

## Deployment

The gameplay server speaks **plain HTTP/WebSocket** — TLS is terminated by a reverse proxy at the deployment boundary. It listens on `SOMNIO_HTTP_HOST:SOMNIO_HTTP_PORT` (default `0.0.0.0:17662`) without certificates. Do not push TLS into the app process; the docker-compose example pins the proxy contract.

Server runtime configuration is resolved from environment variables (`packages/server/src/config.ts`, `packages/data/src/postgresConfig.ts`):

| Variable | Default | Required |
|----------|---------|----------|
| `SOMNIO_HTTP_HOST` | `0.0.0.0` | no |
| `SOMNIO_HTTP_PORT` | `17662` | no |
| `SOMNIO_ADMIN_TOKEN` | `dev-admin` with `SOMNIO_DEV_DEFAULTS=1` | otherwise yes |
| `SOMNIO_SECTORS_DIR` | `packages/core/fixtures/sectors` with `SOMNIO_DEV_DEFAULTS=1` | otherwise yes |
| `SOMNIO_DATABASE_URL` | the `somnio-pg` dev container (`postgres://postgres:postgres@localhost:17663/somnio`, TLS off) with `SOMNIO_DEV_DEFAULTS=1` | otherwise yes |
| `SOMNIO_DATABASE_TLS` | `require` | no (`disable` for a local Postgres) |
| `SOMNIO_TRUST_PROXY` | unset: the per-address pre-login limits are off | no (`1` behind a reverse proxy, `0` when clients connect directly) |

`SOMNIO_DEV_DEFAULTS=1` is the explicit opt-in for every development fallback. The image sets none of it, so a deployment that loses its environment refuses to boot rather than serving `/admin` on a well-known token; an empty `SOMNIO_ADMIN_TOKEN` counts as missing.

`SOMNIO_TRUST_PROXY` says where a client's address comes from, which is what the per-address limits count logins, registrations, `/admin` bearers, and sockets against (see "Wire protocol"). `1` reads the last `X-Forwarded-For` entry, the one the proxy appended itself, and falls back to the socket address when the header is missing or that entry is not an IP address. It is right only when exactly one trusted proxy fronts the server. Behind two, the last entry is the outer proxy's address, which every client shares, and anything that can dial the server directly can forge the header. `0` reads the socket address and ignores the header. Any other value refuses to boot.

Unset or empty, the server limits no address rather than guessing. Counted against the socket address behind a proxy, every client would share the proxy's address, and one person's failures would refuse everyone. The account budget, the login deadline, the character-card deadline, and the total caps on sockets awaiting login and on sockets on the card count no address, so they stay on. Outside `SOMNIO_DEV_DEFAULTS=1` the server logs one error record at startup through the gameplay logger. The `SomnioServer ready` record names the mode in `prelogin_limit`: `proxy`, `direct`, or `off`.

The server exposes `GET /health` (unauthenticated, returns 200 / 503 based on a `SELECT 1`), `WS /ws` (gameplay), and `WS /admin` (operator CLI; pre-upgrade `Authorization: Bearer $SOMNIO_ADMIN_TOKEN` gate — a missing or wrong bearer answers **401**). While the per-address limits are on (`SOMNIO_TRUST_PROXY` is `1` or `0`), an address has ten failed bearers, then one more per minute, so nothing guesses the token at speed. Past that its upgrade answers **429** before the bearer is compared. A correct bearer gets its attempt back. The WebSocket routes are dispatched on the HTTP server's `upgrade` event; the Hono app carries only `/health` and the 401 for a plain request to `/admin`.

The schema is `packages/data/src/migrations/0001_dreamers.ts` plus any migration registered after it, applied on boot. A later migration applies in place, so existing accounts and characters survive it. Migrations are **registered, not discovered**: `migrate.ts` lists them in its `MIGRATIONS` record, so a file added under `migrations/` without an entry there never runs. It refuses a database that still carries an earlier schema (`LegacyDatabaseError`): the Swift-era one, recognized by its `schema_migrations` table, or an earlier TypeScript one, recognized by a `0001_initial` or `0001_metric_world` row in `kysely_migration`. The first migration cannot be applied over any of them; such a database has to be dropped and recreated, the production one and the local `somnio-pg` dev container's alike. The deployment repo records the production procedure, and the `/somnio-server` skill the local one.

`docker-compose.example.yml` runs the full topology — `db`, `server`, `web`, and a `proxy` that is the public surface. The proxy serves the client at `/` and routes `/ws`, `/admin`, and `/health` to the gameplay server; production replaces it with Traefik doing the same split by router priority. The client's endpoint is origin-relative, so `/` and `/ws` **must** share an origin. `web` is `expose`-only, but `server` also publishes `127.0.0.1:17662` alongside the proxy, loopback-bound. That mapping is load-bearing for the `wire-conformance` CI job, which dials the server directly rather than through the proxy. Production publishes only the proxy. The server, `web`, and `proxy` all listen on `8080` inside the network, so the server's published mapping is `127.0.0.1:17662:8080`. That inner `8080` comes from the image's own `ENV SOMNIO_HTTP_PORT`, which the compose file deliberately leaves unset so a dropped `ENV` fails the health check instead of being masked.

The root `Dockerfile` is a `node:24-alpine` multi-stage build: a `deps` stage runs `npm ci --omit=dev --workspace packages/server` over the workspace manifests, and the runtime stage copies that install tree whole (so the `node_modules/@somnio/*` symlinks keep resolving into `packages/*`) plus the four server-side packages' sources and the committed sector fixtures at `/opt/somnio/sectors` (the `SOMNIO_SECTORS_SOURCE` build-arg, default `packages/core/fixtures/sectors`, guarded so an empty or sector-less source fails the build rather than the first boot), so the image carries the world it serves. It takes a **required** `BUILD_VERSION` build-arg (no default; the build fails without it), exposed as `ENV SOMNIO_SERVER_VERSION`, which the admin `version` verb reports.

The server image upgrades the system CA bundle at build time, in a step that never comes from the build cache, so a rebuild picks up a distrusted CA's removal without waiting for a new base image. Its `ENV NODE_OPTIONS=--use-openssl-ca` makes Node verify TLS, which for the server is the Postgres connection, against that system store. Without it Node uses its own bundled CA list, which only a Node release updates. `--use-system-ca` would not do, because it adds the system store to the bundled list rather than replacing it. The `docker-smoke` job asserts that the running server carries the setting. The web image's nginx makes no outbound TLS connection, so it trusts no CA store.

## Code Conventions

- **Exhaustive switches**: `@typescript-eslint/switch-exhaustiveness-check` is on, and the message and state switches list every case so a new tag is a type error, never a silent fallthrough.
- **Literal sets**: a vocabulary (`GAITS`, `ENTITY_KINDS`, `SECTOR_KINDS`, `ROLES`, `CONDITIONS`, `PEOPLES`) is an `as const` array with its union derived from it, pinned to its literals by a test. A wire vocabulary is validated on decode with `requireStringEnum`. `PEOPLES` is the exception: it lives in core, which protocol cannot import, so `createCharacter.people` decodes as a string and the character handler checks it. The `people` the server sends, on a `characters` entry and on `enterSpace`, decodes as an id, and the client draws only a people it knows. Teaching ids are the same kind of exception: `TEACHINGS` lives in core, so a `teachingId` decodes as an id (lowercase letters, digits, and hyphens) and the space checks it.
- **Identifiers in English**: types, properties, message names, Postgres column names, file names; only user-facing strings stay localizable.
- **Testing**: Vitest, one project per package; integration suites under `test/integration/` start their own Postgres. A live-server suite polls the router down to zero players in `afterEach`: a closed socket's server-side unregister and `leave` broadcast outlive the client's close event, so without it the next test's joiner can receive the previous test's stale `leave`.
- **No `.turbo/` references** in code or comments.

### Localization

Every user-facing string is looked up through a bilingual `{key: {en, de}}` JSON catalog whose keys **are** the English source strings, so an unresolved key falls back to readable English rather than a developer identifier. Three catalogs ship: `packages/core/data/catalog.json` (the names of the peoples, roles, items, teachings, nightmares, and the places a trial names), `packages/cli/src/catalog.json` (the twelve admin lines), and `packages/web/src/i18n/catalog.json` (everything the browser renders that the core catalog does not define). `packages/core/src/i18n/catalog.ts` holds the shared reader, merger, formatter, and `catalogViolations`, which checks an allowlist of rendered keys for en/de presence, placeholder parity (`%@` / `%1$@`), and the no-Unicode-ellipsis rule — ASCII `...` throughout.

Each consumer pins its allowlist: `RENDERED_KEYS` in `packages/web/src/i18n/index.ts` and in `packages/cli/src/catalog.ts`. `packages/web/test/i18n.test.ts` additionally scans every `.ts` file under `src` for `t(...)` / `lookup(...)` literals and fails on any that is absent from `RENDERED_KEYS`, and on any allowlisted key nothing renders. The web merge reports collisions between the core and web catalogs and a test pins that set to empty, so a duplicated key fails rather than letting import order pick the winner.

World words are English, and cosmology and the peoples' names are Latin. German translates the English and leaves the Latin as it is. NPC dialog is the one server-rendered text that is translated. A sector file holds each `dialogScript` in English, and `packages/core/data/dialog.json` maps each English step to `{en, de}`. `localizedDialogLine` looks a step up, says a step the catalog lacks as written, and substitutes `$name`. It is a catalog of the same shape, held to `catalogViolations`. A core test requires an entry for every step a committed NPC says. Each entry's German names the player as often as its English and stays within the say cap once every `$name` becomes the longest character name.

### Wire protocol

Messages are a discriminated union in `packages/protocol`, serialized as JSON over WebSocket **text** frames in the shape `{"tag":"<verb>","payload":{...}}`. `encodeSomnioMessage` / `decodeSomnioMessage` are the framing entrypoints; every payload field is validated on decode (typed ranges, byte caps where the protocol declares them), and an unknown tag throws `UnrecognizedTagError`, distinct from `WireDecodingError`, which is what lets the admin route answer `unknownCommand` instead of closing. `AdminRequest`/`AdminResponse` follow the same `{tag, payload}` shape with a string payload. The server decodes every inbound frame before it judges whether that client may send its tag, so every decoder is reachable before login, a server-only message's included. An array in a payload therefore has its count capped before any per-element work. `mapArray` and `requireEntityIds` take that cap as a required argument.

`encodeSomnioMessage` throws `OversizedFrameError` if the JSON exceeds `maxFrameLength`; `MAX_WIRE_FRAME_SIZE` (the `ws` `maxPayload`) sits a small `frameSizeSlack` above it. A frame past the wire size closes 1009 before the decoder runs; a frame inside the slack window reaches the decoder, whose own cap closes 1002 with the reason `frame validation failed`. That is the reason every malformed, unrecognized, or state-illegal frame closes with. Over-cap *values* inside a valid frame (a `clientSay` over 256 bytes, a session token over 256 bytes) are handled, not closed on: the say is dropped and the session verbs answer their failure result, so the socket stays open and the next frame is still processed.

JSON keys are the property names — renaming a property changes the wire key, which only the golden-frame suite catches. Avoid raw dictionaries on payloads; prefer ordered arrays (e.g. the `EntityMove[]` of a `moves` frame) for stable, self-documenting output.

Lengths are metres, with `x` running east and `z` south. Positions are in the coordinates of the player's space, headings are degrees (0 = south, 90 = east), and numbers are plain JSON doubles. Entities carry string ids: a player its character id, an NPC `npc:<sector>/<id>`, a monster `monster:<n>`.

The server handles inbound frames strictly one at a time: the socket is paused while a handler runs and resumed after, so a handler that awaits Postgres never interleaves with the next frame. Broadcasts go through per-connection outboxes with a high watermark; a client that cannot keep up is closed with `outbox overflow` (1008) rather than back-pressuring the space.

**Pre-login limit.** Logins, registrations, and `/admin` bearers are budgeted per client address, in memory (`packages/server/src/connection/attemptLimiter.ts`). An address has ten failed logins, then one more per minute. It has ten registrations that passed validation, then one more per five minutes. A login whose password verifies gets its attempt back, whatever the authentication then answers. A failed login keeps it spent, including one whose account lookup throws, and so does every registration. Past the budget the server answers `loginResult` or `registerResult` with the result `throttled`, before the account lookup or the password hash. The socket stays open. A `redeemSession` is never limited, so a remembered session resumes while its address is throttled. IPv6 clients share a budget per /64. These address budgets are off unless `SOMNIO_TRUST_PROXY` is `1` or `0` (see "Deployment").

Failed logins are also budgeted per account, ten per email across every address, then one more per minute, so guessing spread over many addresses still slows on one account. The budget counts emails, not addresses, so it is on whatever `SOMNIO_TRUST_PROXY` says. Past it a login is answered `throttled` before the lookup and the hash. The address budget is checked first, so a throttled address cannot drain an account's. The key is `postgresNormalizedKey` in the data package, the value of the `email_normalized` column, so every spelling of one account's email draws on one budget. An email no account holds counts the same. Only a verified password gives the attempt back.

An email with a control character or a lone surrogate is answered `badCredentials` before either budget, since no account can hold one. Registration refuses both too. A lone surrogate reaches Postgres as U+FFFD, so two such spellings would be one account under two account budgets. A rejected login's log record names a known account by its id and never carries the submitted email, because the gameplay log is readable over `/admin` and the email field may hold a password typed into the wrong field.

The address table and the account table each hold at most 10 000 keys and fail closed. Once one is full, a new address or email is answered `throttled`, and a new address's `/admin` upgrade 429, until idle entries are evicted a few minutes later. A flood can refuse newcomers for that long; unbounded memory is the cost this avoids.

Gameplay sockets that have not logged in are bounded too (`packages/server/src/connection/socketAdmission.ts`), because each holds an actor and an outbox. A socket still not logged in 30 s after its upgrade is closed 1008 with `login timed out`, whatever frames it sends. The server holds at most 128 such sockets and answers any upgrade past that 503, whatever `SOMNIO_TRUST_PROXY` says. While the per-address limits are on, one address may also hold at most 8, and its upgrade past that answers 429. The deadline and the ceiling are what bound memory; the per-address cap only stops one misbehaving client.

Authentication, a verified login or a redeemed session, ends that deadline and starts the character card's. A socket on the card is closed 1008 with `character card timed out` after 10 minutes without a request there, so a forgotten tab does not hold its account, and the browser returns to the login card. Each request on the card starts the 10 minutes again. Authentication also trades the socket's slot for one among the sockets choosing a character, a second ceiling of 128. While the per-address limits are on, one address may also hold at most 8 of those. Registration is open, so these caps count sockets rather than accounts. An authentication past either cap gets no `loginResult`: the socket is closed 1013 with `too many players choosing a character`.

A socket keeps its slot, of either kind, until its player is in the world or its connection's exit path has finished, because a handler still awaiting Postgres holds its actor after the socket closes. A stalled database therefore fills the 128 pre-login slots, and upgrades answer 503 until it answers again.

**Characters.** `register {email, password, passwordRepeat}` creates an account, and `login {email, password}` logs into it. The email is the account's login, unique whatever its case or NFKC spelling. Only the shape of an address is checked (one `@`, something before it, a dot in the domain), because nothing is ever sent to it. A taken email is answered `registerResult emailExists`. An account holds at most `maxCharactersPerAccount` (4) characters, each with a name and a people. A character's name goes through the name policy (`validateCharacterName` and the confusable skeleton) and is unique across the world.

A login or a session redeem is answered `loginResult ok`, then the `sessionToken` a login asked for, then `otherSessions {count}`. The connection is then `authenticated` and holds a place on the card (see "Pre-login limit"). It accepts only `createCharacter {name, people}`, `selectCharacter {characterId}`, `deleteCharacter {characterId}`, and the revoke verbs; any other tag closes it. A login next receives `characters {characters}`, each character's `id`, `name`, `people`, and `role`. The newest `last_seen` comes first, then names in code-unit order (`compareCharacters` in the data package, which no database collation changes). A redeem instead joins the character played last at once. It receives `characters` only when none of the account's characters was ever played, or when that join fails (after `characterResult failure`). A character is created with `last_seen` at the epoch, and every join writes it.

A create or a delete is answered with the new `characters`, then `characterResult ok`. A refusal gets `characterResult` alone (`nameExists`, `nameNotAllowed`, `full`, `failure`). Selecting a character joins it. An id that is not one of the account's is answered `failure`, whether selected or deleted.

**Joining.** `enterSpace {spaceId, selfId, people, worldSeconds}` is the first frame of every join (a chosen character, a resume, a door transfer, waking after giving up, and the restore after a failed transfer), and the client resets its world on it. `people` is the joining character's, which a resume straight into the world learns from nowhere else. A `sector` frame for the player's sector and each sector touching it follows, then the player's own `entity`, `inventory`, `energy`, `lucidity`, an `entity` per visible entity, and a `raising` per raise under way on a visible fallen player. `worldSeconds` is the only time the wire carries: the client runs the clock forward from it at `WORLD_TIME_RATE`. The first `energy`, `inventory`, and `lucidity` frames after an `enterSpace` are the baseline, so the client announces in chat (coins gained, a rank, a finished task) only what a later frame changed.

Authentication reserves its account in the router before it reads anything of it, and keeps it reserved while the player chooses, so no second browser can sit on the same card. A socket closing on the card releases it at once, with nothing to write. A disconnect from the world keeps the account reserved until its checkpoint has been written, so a login racing a disconnect is answered `alreadyLoggedIn` rather than reading the rows from before.

**Interest.** A player is sent their own sector and the sectors touching it, and sees the entities standing in them. When an entity's sector changes, every player whose view of it changed gets `entity` or `leave` with `leftGame: false`, whether or not they moved. When a player's own sector changes, they are sent each sector that entered their view, including one they held before, because the server keeps no record of what a client holds. They are also sent a `raising` for each raise under way that came into view with those sectors. The client never drops a sector it was sent: it only stops drawing the ones outside its predicted sector's neighbourhood.

**Movement.** The client predicts and reports: `move {x, z, facing, gait}` about ten times a second, plus a waypoint whenever the straight line from its last report to its next step would be illegal.

The player walks where a press sends them (see "A press on the play field" above), and `GameplayPredictor` takes every step through `resolveMove`. A tap's walk is a path, followed waypoint by waypoint (`PATH_FOLLOWING` in `packages/web/src/client/predictor.ts`). A steer heads straight for the ground under the held pointer, gliding along walls and round bodies, and becomes a path to where the pointer came up. A leg that brings the player no nearer for 0.25 s has its path searched again round the bodies where they stand by then, and a search that finds no way waits 0.25 s and tries again. One destination gets its first search and four more, then the walk ends, so a rare unwalkable leg stops or re-routes the player rather than earning a correction. A new walk replaces the one under way. A press on the player's own body, a fall, a correction, and an overlay end it, and so does a lost pointer for a steer, while a path goes on through chat focus, a hidden tab, and the window losing focus. How a walk meets a door is under "Doors".

Paths come from `findPath` in `packages/core/src/pathfinding.ts`, an A* search over walk rasters. The rasters share one grid of 0.25 m cells anchored at the space's origin, so the cells of neighbouring sectors line up and a path crosses a border on shared neighbours. A sector's raster holds the cells whose centres lie in its rect, each with a bit for a clear centre and one for each of its four forward edges, from the static world alone. `ClientWorld` computes it when that sector's frame arrives and again when a touching sector's does, since an edge with no held neighbour blocks. It keeps a sector's raster until the one for its current inputs replaces it, and drops a result asked for before a later one. A sector with no raster yet blocks every search, so a walk asked for just after `enterSpace` waits for it. The rasters are computed in a module worker (`walkRasterizer.ts`), inline where there is no worker or it fails, through the `workerJobs` helper (`packages/web/src/workerJobs.ts`) the ground field uses too. A search looks within the start and the goal plus 10 m, under an expansion cap, and plans round a disk about every NPC, nightmare, and other dreamer the client draws within 16 m. Where the goal cannot be reached, the path ends at the reachable cell nearest it.

Every part of the pathfinder judges a step by one rule, `legWalkable`: a leg is walkable when every sample along it is clear at the full `playerRadius` and it never nears a body's centre within contact (`bodyBlocksLine`, the follower's `bodyBlocks` at any spacing of its steps). The rule uses the full radius, not `isLegalMove`'s path tolerance, because the follower tests each step at the full radius and would stop dead on a corner a leg grazes within the tolerance. The search's edges, the string-pulling of cells into legs, the goal's end point, and the retry without an edge a leg found unwalkable all apply it, so no part hands another a step it refuses, and a walk can always leave a body it touches.

Facing is independent of travel. On a fine pointer the player faces the point under the cursor at body height, 0.8 m above their feet (`WorldScene.aimPointAt`), so pointing at a body drawn above its feet aims at it, or their target where it is drawn while the gaze is locked on it. A finger has no cursor, so on a coarse pointer they face their target where it is drawn, or the way they walk without one. The gait is a jog. Run, a toggle on the HUD and on Shift that holds across spaces for the session, reports `run`, and a winded player walks whatever it says.

The server accepts a move when its length fits the player's allowance and `isLegalMove` passes (colliders, blockers, ledges, the step-height limit, NPCs); otherwise it answers `correction {x, z}` with the last accepted position. The allowance accrues on the server's clock at a little over running speed and holds two seconds' worth. Length is checked first: a move longer than the allowance is refused and spends nothing, and a move the allowance covers spends its length whether or not its path is legal. The predictor never reports a position its own `isLegalMove` refuses, so an honest client that stays standing is corrected only when its reports were held back for longer than the allowance holds and then arrive together. Players are not checked against each other or against monsters on the server: each client stops its own player at the others where it draws them.

Accepted moves and monster steps go out batched in a `moves` frame per connection every 100 ms, which the client interpolates. The decoder caps a frame at `maxMovesPerFrame` moves, so when more moved in view the server splits the batch across frames. A monster is in it only when it moved or turned.

**Doors.** `useDoor {sector, doorId}` moves the player to the counterpart door's space, and is answered with `doorRefused` when the player's space has no such live door, the player stands outside its trigger (widened by `doorUseSlack`), or the player lies fallen. The client sends it when a walk heading through the door steps into the trigger and then reports nothing until `enterSpace` or `doorRefused` arrives. A path takes the door it ends at, which ends it, since its destination lies in the space left; a path that only passes a door walks on through its trigger. A steer takes a door on entering its trigger, and from within it only on stepping toward the doorway, so a player a path left standing in a trigger can steer back out. A refused door is not asked for again until a step has left its trigger. A press still held through a door steers on toward the ground under the pointer once the player stands in the space it leads to. The two doors of every committed pair face opposite ways, so that steer carries the player away from the door they arrive by.

**Acting.** Walking into an entity asks nothing of the server. An NPC greets a player who comes within `npcInteractionRadius` with the first step of its script, unasked: once per approach, and not again within `npcGreetingPauseSeconds`. `talk {npcId}` asks it to go on. It says the steps after the greeting to that player, the first at once and the rest a cooldown apart, and the request is dropped from outside the radius. `npcId` is the NPC's entity id, here and in the requests to a master.

`target {targetId?}` chooses the entity a player acts on, the player themselves included, or none. One out of the player's view is dropped silently. Choosing does nothing to the entity, and a fallen player may still choose. The server sends that player `vitals {entityId, health}`, a share of the maximum to two decimals, for their target, never for themselves, since their `energy` already says it: at once for one newly targeted, then on a change, at most every 0.25 s. An NPC is always whole. A target that leaves the player's view is let go on both sides. Targets are per space and not saved.

`engage {on}` switches slot 1 on or off. Off is always taken. On is taken only from a standing player whose target slot 1 can act on at that moment (`engageAction` in `packages/core/src/combat.ts`): a standing nightmare in view, with bare hands or a weapon in hand, or a dreamer in view, the player included, for a Healer with the Moonstone in hand. A refusal is dropped silently, so a Healer holding the Moonstone cannot switch it on at a nightmare. While it is on at a nightmare, the server swings at the target alone, at the swing rhythm, and only while the target stands in reach inside the swing arc of the facing last reported (`swingMeets`). Nothing else in reach is struck. A swing not made, with the target out of reach, behind the player, or more balance due than they have, costs nothing. While it is on at a standing dreamer, the server mends them once per touch interval while they stand within `COMBAT.mend.reach` (3 m, centre to centre, `mendReaches`), for `COMBAT.mend.spiritCost` each. Short of spirit, or with the dreamer at full health, it waits and stays on. A Healer who targets themselves mends themselves this way. Slot 1 stays on when the target changes to another it can act on. It goes off when the target is driven off, leaves view, or gives way to one it cannot act on, when a `target` is refused, when the Moonstone leaves the hand of a player whose target is a dreamer or comes into the hand of one whose target is a nightmare, and when the player falls. Like the target, it is per space and not saved.

On a fallen dreamer, Mend raises instead, by touch: within `reaches`, contact plus `COMBAT.reachSlack`. Every Healer engaged on them within touch raises them together. Beginning a raise needs a rank of `drawing-back` and the spirit a whole raise costs on hand, so a lone Healer can finish it. Joining one under way needs the rank, a mend's worth of spirit, and room among the `maxRaiseHealers` Healers one raise holds at most. A dreamer the toggle mends who falls keeps it on, since Mend raises them. `useItem {slot}` uses the Moonstone in hand on its holder. Every mend, on another player or on oneself, goes out as `mend {targetId}` to each player who sees the mended player. It carries no amount, because a player learns another's health only as its `condition`, or as `vitals` while they target them. Nothing a player sends harms another player.

**Trading.** `buy {npcId, itemId}` and `sell {npcId, itemId}` are requests to the `shopkeeper`, under the same gate as a master's: a standing player within `npcInteractionRadius`. The wares, their prices, and the buy-back share are `SHOP` in `packages/core/src/shop.ts`, and its `canBuy` and `canSell` are the rules both sides read. A player carries at most one of each ware, and a ware sells back for half its price, rounded down. The purse and the Moonstone are never traded. A weapon sold from the hand leaves the hand empty. A refused trade is dropped silently. A trade is answered with one `inventory` frame carrying `trade {kind, itemId, coins}`, so the purse and the row change together. The client announces the trade from it instead of the coins gained. It is saved by the next checkpoint, like every other inventory change.

**Speech.** `clientSay {text, kind}` says a line as a `whisper`, `say`, or `yell`. Each kind is heard whole within its clear radius, crumbles across a band out to its reach, and is not heard past it (`SPEECH` in `packages/core/src/speech.ts`: 1.5 / 3 m, 6 / 12 m, 40 / 80 m). Sector interest plays no part. Every other player in the space within reach gets `serverSay {entityId, name, kind, text, clarity, x, z}`, and the speaker's own client draws the line itself. The server crumbles the text at each listener's clarity, so no client can undo it. In the band at least one word is always missing, each run of missed words reads `...`, and `clarity` falls from 1 toward 0. Every listener's crumble of one line draws on the same rolls, so a listener further off misses every word a nearer one missed, and listeners who compare notes learn little more than the nearest heard. `x`/`z` is where the voice comes from in the listener's space. An NPC's lines follow the `say` rule from where it stands. The dreamer it addresses stands within `npcInteractionRadius`, inside the clear radius, so they always hear its lines whole.

An NPC's line reaches each listener in the `locale` (`en` or `de`) their `login` or `redeemSession` named, or in English when it named none. The connection keeps the locale until it closes, and nothing saves it. The server renders the line in that language before it crumbles it. The rolls are shared across languages, but a further listener missing every word a nearer one missed holds only within one language: an English and a German listener of one NPC line can piece together more than either heard. Player speech is never translated.

A yell also goes one door further, into the space beyond a live door. A listener there hears it from the counterpart's doorway, by the shortest way through. That way runs from the yeller to the door, plus `doorMuffleMetres`, plus from the doorway to the listener. The muffle is larger than a yell's clear radius, so a voice through a door always crumbles. It is not relayed again. `entityId` names the yeller even there, so a client whose bubble for them is placed by the door hangs it over their head once they come through.

**Pools and condition.** The rules and every number are in `packages/core/src/combat.ts`, shared by both sides. `energy` carries a player's exact pools, as whole numbers, to that player alone, on every change. Everyone in view learns another entity's health as its `condition`, and only the player who targets it learns more, from `vitals`. The condition is `hale` only at full health, then `grazed`, `wounded`, `hurt`, and `failing` by quarters of the maximum, and `fallen` at none. Each `entity` frame carries it, and `condition {entityId, condition}` goes out only when the band changes. `blow {attackerId, targetId, hit}` announces each swing and each strike. Balance drains by the distance run and recovers on the server's clock by the gait last reported. Winded is never sent: server and client each start it from the balance at the join and fold the same rule over the same `energy` frames. The server does not shorten a winded player's allowance, so an honest client is still never corrected for it.

**Falling, raising, waking.** A nightmare's strike that takes the last of a player's health is the only way to fall. The fall comes with a `correction`, because the client may have predicted a little past the last accepted position. A fallen player's moves are answered with `correction`, their `talk` and service requests and an `engage {on: true}` are dropped, and they can still choose a target and speak, a yell included.

`raising {targetId, healerIds, state, progress, seconds}` is a whole snapshot of a raise. It goes to everyone who sees the fallen player's sector when the raise begins, when its Healers change, and when it ends, and to a player who comes into view of one under way. While `holding` it names the Healers holding on, those engaged on the fallen player within touch, in the order they took hold, the share done, and the seconds left at their pace. `done` and `broken` name those holding on just before the end.

Each Healer holding on adds a pace, so two finish the raise in half the time. Each pays spirit for the seconds they held. A Healer drops out when they switch slot 1 off or target another, move out of touch, put the Moonstone away, run out of spirit, fall, or leave. That takes away only their pace, and the raise goes on from where it stands. It breaks, and starts over from nothing, only when the last of them drops out. Taking hold, to begin or to join, spends the Healer's touch, as a mend does, so a Healer stepping in and out of reach takes hold at most once a touch interval while they stay in the space. Their Moonstone reaches no one for that interval. Each Healer who held on and is still in the space when it is done earns their share of the practice, by the seconds they held.

`wake {}` from a fallen player transfers them to the wake-point: the `spawn` of the `EdariaInn` sector, or the starter spawn when that sector is missing or has no `spawn`, which the server logs at boot.

**Lucidity.** `lucidity {role?, ranks, study?, task?}` is what a player has grown into, sent to them alone at each join and on every change. The rules are in `packages/core/src/lucidity.ts`. `askTask {npcId, teachingId?}`, `completeTask {npcId}`, and `study {npcId, teachingId}` are requests to a master, an NPC carrying a master's `service`. Each is dropped silently unless the player stands within `npcInteractionRadius` of it. A player with no role asks either master for that master's trial (`askTask` with no `teachingId`). Once the trial is done, `completeTask` at the same master makes the role theirs. A gate's task and a teaching to study are asked of the master of the player's role. `abandonTask {}` works anywhere.

**What breaks the wire.** `helloVersion` (`packages/protocol/src/constants.ts`) is compared with strict equality by the client; bump it when the wire breaks. Registry geometry is part of the movement contract: the client collides against the registry it was bundled with, so a page loaded before a deploy would predict against the old shapes and be corrected by the new server. Changing a model's `colliders`, `walkSurfaces`, or `doors`, or a `footprint` that stands in as its collider, is a wire break. A change to the shared geometry that moves a result only by rounding, an ulp at an exact clearance boundary that honest play cannot reach, is not.

### Sector format

Sectors are JSON, stored in `.somnio-sector` files, read and written by `packages/core/src/sectorFile.ts`. The writer produces plain JSON with a 2-space indent, recursively sorted keys, and a trailing newline, and leaves defaults out, so committed fixtures stay human-diffable and byte-stable across an unedited open-and-save. The reader checks the file's byte size before parsing (`maxSectorFileBytes`) and bounds the sector's extent, every coordinate, and every record-array count (`SOMNIO_PROTOCOL_CONSTANTS` for the view, `SOMNIO_CONSTANTS` for NPCs and monster spawns), so a hostile `.somnio-sector` cannot drive an unbounded allocation when loaded from `SOMNIO_SECTORS_DIR`. The reader's check runs on text already in memory, so the server's loader refuses a file over that size before reading it. It also refuses anything but a regular file, since a FIFO or a device reports size 0 and reads without end.

A sector file is the **sector view** plus the content only the server acts on. The view (`SectorView` in `packages/protocol/src/sectorView.ts`) is declared once and is exactly what a `sector` frame carries; `decodeSectorView` validates it for both. Property names are the JSON keys, so renaming one changes the file and the wire. The sector's `name` is the filename stem (at most `maxSectorNameUTF8Bytes`, so an NPC's entity id always fits its cap) and never part of the file: the reader injects it and the writer strips it. One record of each kind, in reading order (the file sorts its keys):

```json
{
  "kind": "outdoor",
  "origin": { "x": 0, "z": 0 },
  "size": { "width": 40.96, "depth": 40.96 },
  "ground": {
    "backgroundMaterialId": "grass-meadow",
    "marks": [
      { "id": "plaza", "materialId": "cobble-town", "shape": { "kind": "polygon", "points": [{ "x": 16, "z": 0 }, { "x": 24.96, "z": 0 }, { "x": 24.96, "z": 8 }] } },
      { "id": "road", "materialId": "dirt-path", "opacity": 0.8, "shape": { "kind": "stroke", "radius": 1.6, "points": [{ "x": 2, "z": 20 }, { "x": 38, "z": 22 }] } }
    ]
  },
  "placements": [{ "id": "building-townhall-1", "modelId": "building-townhall", "x": 36.8, "z": 4.48, "yaw": 270 }],
  "blockers": [{ "id": "blocker-1", "x": 0, "z": 0, "width": 5.12, "depth": 0.44 }],
  "doors": [{ "id": "to-edarialibrary", "placement": "building-townhall-1", "anchor": "main", "target": { "sector": "EdariaLibrary", "door": "exit" } }],
  "spawn": { "x": 2.88, "z": 4.32, "facing": 0 },
  "npcs": [{ "id": "pugnax", "name": "Pugnax", "characterModelId": "fighter-master", "x": 37.32, "z": 33.2, "facing": 0, "dialogScript": "...", "service": "fighterMaster" }],
  "monsterSpawns": [{ "id": "spawn-1", "kind": "ghost", "x": 0.64, "z": 1.28, "width": 5.76, "depth": 7.68, "maxAlive": 3 }]
}
```

Lengths are metres, `x` runs east and `z` south, and every record position is relative to the sector's north-west corner. `x`/`z` is the centre of a placement, an NPC, and the spawn, and the north-west corner of a rect (a blocker, a monster spawn's area). Angles are degrees: `yaw` counter-clockwise seen from above, `facing` a heading with 0 = south and 90 = east, normalized on decode.

`kind` is `outdoor` or `interior`. An outdoor sector carries an `origin`, its north-west corner in the one outdoor space, and is lit by the world clock. An interior is a space of its own and carries a `brightness` percentage (0-100) instead, which scales its steady light. Only the light through its door follows the clock. Each of the two keys is rejected on the other kind.

Every record has an `id` unique within its array (lowercase letters, digits, and hyphens, at most 64 bytes), and the decoder rejects a duplicate. Ids are what a door, the editor's selection, and persisted NPC dialog progress refer to, so reordering records changes nothing.

- **Placements** put a registry model (`modelId`) at `x`/`z`, turned by `yaw` (models are normalized with their door or long axis on +X, so 270 faces a door south) and lifted by `elevation` (a candle on a table). A placement blocks through its model's registry colliders. `elevation` is visual only, and is ignored on a model with walk surfaces. An unmapped `modelId` renders a placeholder and contributes no collision rather than rejecting the file.
- **Blockers** are invisible blocking rects for what no model covers.
- **The ground** is a `backgroundMaterialId` and `marks` painted over it in array order. A mark is a `stroke` (a round-capped polyline `radius` wide on each side, at most 10 m; one point makes a dab) or a `polygon` (at least three points, filled even-odd), in one `materialId` at an `opacity` from 0 to 1. Every mark's edge fades over `markFeatherMetres`, broken by noise reaching at most `markEdgeNoiseMetres`, so no mark has a hard edge. Its paint may reach at most 1.5 m past the sector's rect, so a mark only ever paints the sector and those touching it. `markPointBounds` in `packages/protocol/src/sectorView.ts` is the rect its points must lie in, and the decoder refuses a point outside it. A sector holds at most 512 marks and 8,192 points in all, both counted before any mark is decoded. Marks are purely visual, and a material the client has no recipe for is skipped (a background without one draws the first recipe).
- **Doors** are attached to a placement's door anchor (`placement` + `anchor`, the anchor being one of the model's registry `doors`) and name their counterpart (`target.sector` + `target.door`). The decoder rejects a door whose `placement` is not in the sector. The trigger is the anchor's width by `doorTriggerDepth` in front of it, and a player arrives 0.8 m out from the counterpart door, facing away from it.
- **`spawn`** is where a new character enters the world, in the starter sector, and where a dreamer who gave up wakes, in the inn. The starter sector must have one.
- **NPCs** stand at `x`/`z`, drawn with a registry character model (`characterModelId`), and speak the steps of their `dialogScript`: the first as a greeting to whoever comes near, the rest when asked. An optional `service` makes the NPC a master (`fighterMaster`, `healerMaster`) or the shopkeeper (`shopkeeper`), whose panel opens when it is asked. It reaches the client on the NPC's `entity` frame. The reader rejects an NPC standing outside its own sector's rect, because players are told about an NPC by the sector that owns it. It also rejects a step that could pass the say cap once each `$name` becomes the longest character name, because a client closes on an over-cap line.
- **Monster spawns** are areas that keep up to `maxAlive` monsters (at most `maxSpawnAlive`) of one `kind` from `packages/core/src/monsterKinds.ts` alive. The area is also its monsters' home ground, which they never leave, so where it ends is where a dreamer can retreat to. A monster chases only a dreamer standing inside it, and walks back to where it spawned when there is none. It strikes any standing dreamer within its reach, just outside the area too, so the edge is no line to strike from unanswered.

The `spawn`, the NPCs, and the monster spawns never reach a client as records: `sectorView` strips the server-side content, and NPCs and monsters arrive as entities.

Omitted on write and defaulted on read: `yaw` and `elevation` at 0, a mark's `opacity` at 1, empty record arrays and marks, an unset `spawn`, and an NPC's unset `service`.

The server builds the world from the loaded sectors at boot (`buildWorld` in `packages/core/src/world.ts`). Every outdoor sector lies in the one space `outdoors` at its origin, so sectors that touch are walked across with no transition and a sector edge with no neighbour blocks. Each interior is a space named after its sector, reached through a door. Overlapping outdoor sectors, an outdoor sector under `minOutdoorSectorExtent`, a sector named `outdoors`, a spawn a body cannot stand on, and a starter sector without a spawn fail startup.

Two outdoor sectors that do not touch must stand at least `SECTOR_BORDER_SUPPORT_METRES` (4 m) apart, measured from each one's padded raster rect (its rect plus the ground's gutter, snapped to the texel grid) to the other's rect. A client is sent only the sectors touching the player's, so it can blend a sector's ground only with those, and a sector closer than that would paint into a border it is not part of. A pair that breaks this is logged under each of the two, as a `sector` record naming the other, and the world still loads with an uneven seam there. The numbers are in `packages/core/src/ground.ts`, and the check is `spacingIssues` in `packages/core/src/world.ts`.

A door is live only as half of a sound pair: both doors resolve to an anchor, point at each other, and have an arrival point a body can stand on. Any other door is logged and left inert, and the world still loads. Standing means clear of colliders, blockers, ledges, and the space's NPCs, because a body arriving in contact with an NPC could never move again. An unmapped model, an `elevation` on a model with walk surfaces, and walk surfaces of two placements that overlap are logged the same way. A live door whose arrival point lies within a nightmare's reach of a monster spawn's area is logged too, because a dreamer arriving there can be struck before they see the room. It stays live, since the pair itself is sound.

The outdoor lands' dressing and roads are composed by a seeded generator, `packages/core/scripts/compose/` (run by hand: `node packages/core/scripts/compose/main.ts`). `rules.ts` holds each land's roads, clearings, worn ground, density, model mixes, and seed, and mirrors the splash reel's outdoor paths as keep-outs. The generator routes a dirt path from each outdoor door to the nearest street. `rules.ts` also lists the town's compound openings that no door path runs through, each of which gets a path of its own, and the compounds whose two door paths do not meet, which get a path joining them. The generator keeps each model's crown, the circle round its footprint, off every route and keep-out, so no canopy hangs over a path or a splash figure. Over 3 m beside them it thins the dressing from sparse to full, so a route does not run between hard walls of trees. `splash-reel.test.ts` proves the reel's paths legal against the composed lands, so the keep-outs and the reel move together. Every record it writes has an id starting `gen-`. One run strips those from every outdoor sector and composes them again in name order, so composing its own output writes the same bytes. Every other record (the town's walls and buildings, doors, NPCs, a mark painted by hand) is kept as it is, and hand marks paint after the generated ones.

The rooms' walls are ordinary placements of the stone and plaster-and-timber wall sets, with their inner faces on the sector's edge. The walls are full on the north and west edges and low on the south and east, because the camera looks in from the south-east. Each room chooses which sections of its back walls are windows, and keeps anything tall or wall-hung off those sections. Each door is a low threshold of its wall set (`timber-room-threshold`, `stone-room-threshold`) lying across a two-module gap. Its anchor is on the wall's inner face, and a mat lies just inside. A room's floor is its background material. A boarded floor within it (the Fighter Hall's sparring floor, the Arena's refuge, the strip by its door beyond every ghost's reach) is laid from `floor-boards` tiles, one module each, because a painted mark would blend at its edge.

The canonical `.somnio-sector` extension is used everywhere: the committed fixtures (`packages/core/fixtures/sectors`), the server's `SOMNIO_SECTORS_DIR`, and the web editor's file API. The server loads only `.somnio-sector` files and keys each by its extension-stripped filename (the filename-as-sector-id convention door targets rely on); a directory with no `.somnio-sector` files fails startup (`noSectorsLoaded`) rather than booting an empty world.

### Model registry

The 3D pack's layout and its collision geometry are data: the committed `packages/core/data/ModelRegistry.json` (exported as `@somnio/core/data/ModelRegistry.json`) holds `characterModels` (character model ids to model stems, each with its `expectedClips` clip-presence contract), `playerModel` (the one character model every player uses), and `objectModels` (semantic object ids to prop stems and their geometry). The player's model and each nightmare also expect the clips that play once: the fall, a swing, and a flinch. The registry references only filename stems, so it never drifts from the uncommitted, operator-supplied model pack.

An object model's geometry is in model space: metres, the origin at the ground-footprint centre, +X east and +Z south at yaw 0, a rect's `x`/`z` its minimum (north-west) corner. A placement is tested in its model's space, so axis-aligned registry rects work at any yaw.

- `footprint` is the measured ground bounds, centred on the origin.
- `colliders` are the rects that block. Left out, they default to the footprint; `[]` never blocks (`rug`, `candle`, `door-mat`, the wall-hung pieces).
- `walkSurfaces` are rects with one `height` each, a stair run being one rect per tread. A body steps between two heights up to `maxStepHeight` apart (the ground is 0), and every stretch of a surface edge with a larger drop is a blocking ledge.
- `doors` are the anchors a sector's door records attach to: `id`, `x`, `z`, a cardinal `facing` out of the door, and the opening's `width`.
- `light` is the flame a model carries: a point in model space, `y` above its ground, and a `kind` from `LIGHT_KINDS` (`candle`, `hearth`, `lamp`, `torch`) that the client lights by its own values. Every placement of the model in a room is lit, so an unlit variant needs a model of its own.

`packages/core/src/modelRegistry.ts` validates the structural invariants on read: non-empty stems and ids, no duplicate ids, characters expecting at least one clip, a `playerModel` that is a character model, positive sizes and heights, cardinal door facings, walk surfaces of one model that do not overlap (steps cut into a plinth would otherwise resolve to the plinth's height), and lights of a known kind not below the ground. The browser degrades to a placeholder registry with a logged error; the server parses the same file strictly at boot and fails startup on an error, because an empty registry there is a world with no collision and every door inert.

The web editor's model, character, and door-anchor pickers are populated from the same registry, so the authoring surface can only reference what resolves. The asset pipeline's clip-presence and footprint gates read the same file, and its `Pipeline/glb_surface_report.py` is where a model's footprint, colliders, walk surfaces, and door anchors are measured.
