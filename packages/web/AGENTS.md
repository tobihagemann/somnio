# Browser client (`packages/web/`)

The instructions are split by package, and a section named in a "see ..." lives in one of these files:

- `AGENTS.md` (repository root): tech stack, package graph, build and test, logging, deployment, lint and format, code conventions, localization.
- `packages/protocol/AGENTS.md`: the wire protocol's framing, the pre-login limit, characters, joining, interest, and what breaks the wire.
- `packages/core/AGENTS.md`: the gameplay rules and their frames (movement, doors, acting, abilities, threat, elites, bosses, gear, trading, drops, speech, pools, raising, fixtures, lucidity, quests, the bounty board), the sector format, and the model registry.
- `packages/web/AGENTS.md`: the browser client, the web map editor, the web asset pack, and hosting.

A Three.js client that speaks the wire protocol through the shared `@somnio/protocol` package.

```
npm run dev --workspace packages/web      # Vite on :17669, proxying /ws to the local server on :17662
npm run editor --workspace packages/web   # Vite with the editor entry + sector file API (see "Web map editor")
npm run conformance                       # wire conformance against a LIVE server (SOMNIO_CONFORMANCE_URL)
```

## What holds the client and server together

The protocol and core packages are shared code, so the two sides cannot disagree about a message shape. They also run the same movement rule (`packages/core/src/collision.ts`) over the same sectors and the same registry geometry. Two suites guard the parts that are not shared:

- **Golden frames** (`packages/protocol/fixtures/golden-frames.json`) are compared as canonicalized JSON (object keys sorted) by `golden-frames.test.ts`. This is the check that catches a payload **property rename** — the round-trip suites encode and decode with the same renamed property and stay green. Re-record deliberately with `SOMNIO_RECORD_GOLDEN_FRAMES=1 npx vitest run --project protocol`.
- **Wire conformance** (`packages/web/test/conformance/`) drives the real TypeScript encoder and transport into a real server. Its outbound case is what proves application frames ship as **text**; everything else in that file passes while the transport sends binary. The over-cap frame case accepts either close code in `[1009, 1006]`: the client is still writing a ~1 MiB payload when the server refuses it, so whether the close frame arrives before the reset is transport timing.

## Browser-only decisions

- **Session tokens.** A browser page needs a refresh to survive, so the server issues a resumable token on `Login.requestSessionToken` and accepts `redeemSession`/`revokeSession`/`revokeOtherSessions`. Issuance is **request-gated** on that optional field: a client that never asks receives no `sessionToken` frame. `revokeOtherSessions` is the game menu's Log Out Other Browsers. It deletes the account's other rows and spares the token the connection redeemed or was issued, the one this browser holds. Its answer, `otherSessionsRevoked`, counts the unexpired rows it ended. Unlike `revokeSession`, it leaves this browser logged in and in the world. A login or a session redeem reports `otherSessions {count}`, the account's other unexpired rows, and the menu offers the action only while that count is above 0. One account has one live connection, so no other browser can add a row while this one plays. The count can therefore only fall until the next login or redeem.
- **DOM UI over WebGL.** Panels and overlays are real elements, so password managers work and `agent-browser snapshot` sees them. `packages/web/src/ui/chrome.css` draws the Kenney 9-slice chrome with `border-image-slice: 36` against an 18px border — the slice is unitless _image pixels_.
- **The orthographic camera's `scale` is a vertical HALF-height**, so the Three.js mapping is `top/bottom = ±scale`, `left/right = ±scale × aspect`. The usual `frustumSize / 2` idiom halves it again and renders the whole world at 2x. The game's default is 7, 14 m shown top to bottom (`ORTHO_RIG` in `packages/web/src/scene/cameraRig.ts`). The player zooms by the wheel or a pinch between 0.78 and 1.4 times that (`PLAYER_ZOOM`), a half-height from 5 m to about 9 m. The editor keeps a zoom range of its own (`EDITOR_ZOOM`).
- **Resize holds the vertical world extent constant.** A gameplay contract, not a rendering detail: a bigger window magnifies rather than reveals. Name plaques and speech bubbles are sized in metres too, but never drawn smaller than 1.2 CSS pixels per pixel of their art (`OVERLAY_MIN_SCREEN_PIXELS` in `overlayArt.ts`), so their text stays readable on a small window or a phone.
- **The ground is painted, not textured.** Each sector's ground is one plane whose shader draws every floor material from a procedural recipe (`packages/web/src/scene/groundMaterials.ts`, the one list of floor-material ids) by two weight textures. `groundField.ts` computes those weights from the sector's background, its touching outdoor neighbours' backgrounds (blended over 5 m in noisy patches), and the marks of all of them. One field takes tens of milliseconds, so `groundRasterizer.ts` runs it in a module worker, and inline where there is no worker or the worker fails. Two touching sectors of one texel size (every sector up to 81.92 m across) compute identical weights wherever both rasterize, so their seam cannot show: every input is keyed to space position, marks paint in one order (sector name, then index), and a sector's raster carries a gutter past its edge. The scene keeps drawing a sector's previous field until the next arrives, and paints the player's own sector on the spot before revealing a new space. The grass leans away from what touches it and springs back once let go (`grassSpring.ts`): a body's feet and lower legs, and whatever its hands hold, along the item's length wherever it dips into the grass.
- **A press on the play field acts, walks, steers, picks up, or uses.** A mouse, a finger, and a pen take one path, the primary button only, but for a press on a body (see "One target"). The scene picks by shape what is drawn under the pointer (`WorldScene.pressTargetAt`): first a drop's name, then an entity's body (`WorldScene.entityAt`, a capsule from feet to head as wide as the body is drawn, nearest the camera first, its radius at least 0.6 m on a coarse pointer), then a drop's model as it lies, a little round it (wider under a finger), then a fixture's model (`WorldScene.fixtureAt`, the meshes of the placement that carries it as they are drawn, nearest the camera first), then the ground (`WorldScene.groundPointAt`, which meets the top of a walk surface before the floor beyond it). A body is picked down to its feet, so it covers a drop's model under it. The drop's name stands under its model on screen, below the feet of a body on the drop, so the name is what reaches a drop under a body. A press on a drop walks the player into `PICKUP_REACH` of it and picks it up (see "Drops"). A press on a fixture walks the player into speaking distance of its placement's centre and uses it, at once from within that distance (see "Fixtures and services"). A fixture's model is picked rather than its footprint, because the camera looks down on a tall board and a ray through its face meets the ground about a metre beyond it. A right press on a drop or a fixture does nothing. A press on a body walks the player to it and acts there (see "One target"). The player's own body is no part of the pick, since their own frame is how they target themselves: a press there lands on what lies under it, a drop's model or the ground. A press on the ground keeps the target. Up within 180 ms and 12 px of where it landed (`HOLD_TO_STEER_MS`, `TAP_SLOP_PX`), it is a tap, which walks to where it landed. Held longer or moved further, it steers toward the ground under the pointer, and on coming up walks on to where it came up. A second pointer down makes it a pinch, which zooms and walks nowhere until every pointer is up.
- **One target.** A left press on a body (`GameplaySession.pressEntity`) makes it the target, which a ring marks. On an NPC it walks the player up beside it. On the way it asks the NPC to go on (`interact`) the first time they stand within speaking distance, which opens its panel when it carries a service, or while its quest marker shows (see "Fixtures and services"). So an NPC behind a counter is still asked, from as near as the player gets. On a body slot 1 can act on (`engageAction`), it locks the gaze on it (see below), switches slot 1 on, sending `engage` after `target`, and walks the player up beside it. That walk ends in touch (`reachDistance` in `combat.ts`), which is Attack's reach and a raise's, and lies within Mend's. A Healer who would mend from further off selects the dreamer without walking (a right press, or a finger's rest) and switches slot 1 on with its button or the 1 key. On another dreamer slot 1 cannot act on, it walks the player up beside them all the same. Any other body, such as a nightmare while a quest held forbids striking, it only selects. The walk follows the body, aimed at it again whenever it has moved `FOLLOW_REAIM_METRES` (0.5 m) from where the walk heads, and ends the first time the player stands in range of where the body stands then. A body that moves away after that is not followed, and a nightmare driven off before then stops the walk where the player stands. The press ring drops on the body, moves with it, and lifts as the walk ends, as it does on a fixture or a drop a press walks the player to. From within range already, the walk under way stops and the press acts at once, with no ring. A press on the ground ends the following, and another target stops its walk. A right press on a body (`GameplaySession.selectEntity`), the same pick, only makes it the target, without walking, and slot 1 stays on where it can act on the new target, as at any change of target. A right press on the ground, the ground under the player's own body included, clears the target. A finger and a pen have no right press, so they rest on a body instead: lifted within `FINGER_HOLD_MS` (400 ms) of landing, a press on a body acts as a left press does, and resting that long it only selects. Sliding past `TAP_SLOP_PX` first, it steers as a press on the ground does. A mouse's left press acts as the button goes down. A press on a dreamer's name in the Players window also makes them the target. A press on the player's own frame, or on their own name in the Players window, makes them their own target, and the target frame reads their health from their own `energy`. The ✕ on the target frame clears the target. Escape takes one thing away at a time: the open chat, then a finger's menu sheet, then an item carried in the Character window, then an item's card, then the newest open window, then a carrier's panel, then the walk under way, which stops where the player stands (`GameplaySession.stopWalk`, though a leap runs on), then the target, and only then does it open the game menu. What stands open goes before the walk, since it is what the player means to put away.
- **The gaze lock.** A left press on a body slot 1 can act on locks the player's facing on it, so they face it whatever the cursor does. The target's ring shows the lock and slot 1 together: green while slot 1 is off and gold while it acts, a plain ring without the lock and a reticle with four ticks pointing in while locked. The target frame's accessible name says the lock. A press on the ground walks with the lock kept, so a Fighter backs away still facing the nightmare. A right press on the target changes nothing. The 1 key switches slot 1 alone, so a lock with slot 1 off is a green reticle. The lock also ends with the target: cleared, changed, out of view, driven off, or left behind in another space. The gaze lock's own button (`GazeLockButton` in `belt.ts`) stands before Run on the belt, and beyond Run on a finger's layout. Its key is F (`GAZE_LOCK_KEY`), under the same gates as the belt's other keys. It locks the gaze on the target, any body targeted but the player, or lets go of it (`GameplaySession.toggleGazeLock`). Either way the target and slot 1 stay as they are, so a Healer mends on while facing the cursor. It is the one way to let go of the lock and keep the target. It is drawn as the target's ring, lit as the reticle while locked, and greyed out with nothing to lock on. A finger faces the target only while locked (see "Movement").
- **Slot 1 acts on the target.** It is one toggle, the first slot of the HUD's belt (the big button under the right thumb on a finger's layout) or the 1 key, and a left press on a body switches it on too (see "One target"). What it does there, and when it goes on and off, is `engageAction` in `packages/core/src/combat.ts` and the `engage` rules (see "Acting"), applied alike on both sides. The button is named and drawn for that action, Raise where Mend meets a fallen dreamer. It is lit while on, and the target's ring is gold. At anything else it is greyed out and keeps its last look, so a Healer who puts the Moonstone away finds it greyed out at a dreamer. At a nightmare it cannot attack, it is Attack, greyed out, and its tip says why in red: something in the main hand that does not swing, or a quest held that forbids striking. That is `attackRefusal` in `combat.ts`, the rule `engageAction` reads, so the tip and the slot cannot disagree. The slot and the 1 key never walk the player toward the target. Only a left press on it does. The client slows its own player when a `blow` names them as the attacker, since the server chooses the moment of each swing.
- **Slots 2–6 use abilities.** They hold the abilities the player's ranks teach, in the order of the teachings that teach them (`abilitiesTaught` in `packages/core/src/abilities.ts`), and empty slots after them. A press on one, or the keys 2–6 under the same gates as the 1 key, uses it (see "Abilities and effects"). A slot is greyed out while `abilityRefusal` names a need the player misses (the rule `abilityAllowed` applies), and swept dark while a cooldown runs, its own or the global one, whichever ends later. Its own counts down in whole seconds; the global one only sweeps. The sweep is a CSS animation timed from when the `cooldowns` frame says the cooldown began, so a slot keeps its elements across `energy` frames. Run is drawn held off, and described so, while an effect keeps the player from running.
- **The HUD** (`packages/web/src/ui/hud.ts`, styled by `hud.css`, which the editor does not load). The player's own frame sits top left: their portrait in a ring of their condition, their people's sigil on a badge at its foot, their name, and their people and role. The people comes from each `enterSpace`, so a resume straight into the world draws it too. The target frame sits top centre with the target's portrait. Each frame carries a row of the effects its entity holds, from the `effects` frames: a glyph per effect with its whole seconds left, which keeps its element while the effect holds. The world clock sits top right, as `☾ 22:40` or `☀ 14:05` with the sector's place name (`placeNames.ts`). The client runs the clock on from `enterSpace` (`ConnectionController.worldSecondsAt`), and the sun is up from 6 to 22 (`sunIsUp` in `packages/core/src/worldClock.ts`), which the world's light and a night-only door read too. The belt sits bottom centre: a Health globe and a Spirit globe filled by the exact pools, a Balance arc across its top that turns orange under a Winded tag, slot 1, slots 2–6 for abilities, the gaze lock and Run at its end, and one line saying what the player studies and how far toward the next rank. A globe shows its number and its word only while the pointer rests on it, since its fill already says how full the pool is. Players, Character, Quest log, and Settings sit beside the Spirit globe. The first three open windows, several at once with the newest on top, the Players window and the Quest log beside the Character window while it is open; Settings is the game menu. While a carrier's panel is open down the right edge, every window stands to its left (`GameHUD.setCarrierPanelOpen`), so neither hides the other. In a window too narrow to hold the Character window beside the panel, a window and the panel take turns, as on a finger: the panel opening closes the windows, and a window opening closes the panel. C and I also open and close the Character window, O the Players window, and L the Quest log, under the same gates as the belt's keys, so not while the chat has the keyboard. None of these keys, the belt's included, acts with Alt, Ctrl, or Cmd held, since those presses are the browser's or the system's. Alt+Enter enters and leaves fullscreen, since the browser keeps F11 for its own. It is the page's key rather than the world's, so it works under an overlay too, though not while the chat has the keyboard, and the Options overlay names it over its Fullscreen button. Each window's menu button names its first key in its tip (`WINDOW_KEYS`). A window's title stands alone in its row, centred over the window, and its ✕ is a small chrome button on the panel's top-right corner (`windowHead` in `hudWindows.ts`, which the finger's chat panel uses too), named "Close" and the window's title. Speech bubbles keep clear of every HUD part that shows (`GameHUD.occluders`), the faded chat excepted. On a mouse, in a window too narrow or too short for it, the HUD shrinks evenly (`GameHUD.setViewport`): the frames, the clock, the quest tracker, the line and the banner, and the belt scale toward the edges they stand at, so each stays whole and none overlaps another. A window keeps its width and ends above the menu.
- **The quest tracker, the line, and the banner.** The quest tracker sits under the clock while the player holds a quest (`questTracker.ts`): each quest held, the one that last moved first and the rest in the log's order, with its title and each objective line, its full stop giving way to its count ("Visit Mercus in his shop: 0/1", `objectiveCount` in `questText.ts`), a met line in the markers' grey, and a quest done by its title and where to return, in the markers' gold. Its heading, the Quest log's glyph and "Quests", is a button that hides and shows the list, named for which it does, with "· N" beside it while the list is hidden. The choice is kept per browser in `localStorage`. It does not show while the Quest log is open. While a carrier's panel or a window is open down the right edge, it stands to the left of them where there is room beside the target frame, and else hides (`GameHUD.placeTracker`). Under the target frame, a line says each line of a quest held whose count moved ("Drive off 4 Skeletons in the Graveyard: 2/4", the count in the markers' gold) for 3.2 s, and a newer count replaces it and starts it over. A quest done is a banner there instead, "<title> complete" in gold between the window titles' divider flanks and where to return under it, for 4.5 s, cutting a line short (`questFeedback.ts`). A quest turned in is a banner the same way: its title in gold, then what it granted and paid in one line ("60c · 30 practice toward Toughening", a trial's "You are a Healer · Touch, rank 1", a gate's "Follow-through, rank 1"), then each item it gave by name in its rarity's colour on a line of its own (`turnInSaid` in `questText.ts`). A quest taken on is a banner the same way, one for each quest a frame adds to those held: a small "Quest accepted" over its title, both in gold, then what it asks a line each, as `objectiveLines` says it, the hidden places as one line (`acceptedSaid`). It is said nowhere else, in no count and no chat line, however far the quest has come as it is taken on. One shows at a time. A banner arriving while another shows waits its turn. A count waits behind every banner, and the newest replaces any count that waits. Both come from the session's `onQuestNews`, from the `quests` frames after the baseline, as the chat lines do. A turn-in pairs the frames that answer it into one piece of news. The `quests` frame that moves a quest held to `done` opens it. When the quest pays coins or an item, a trial's Moonstone or wand included, it waits for the `inventory` frame the server sends last, and takes that frame's coins gained and `rewarded` (`GameplaySession.announceTurnIn`). Whether it waits, and what it teaches, follow from the quest by `turnInGrant` in `packages/core/src/quests.ts`, the rule the server's turn-in reads too. Its practice goes toward the teaching studied as the `quests` frame arrives, so the `lucidity` frames between add nothing it needs. A join drops a turn-in still waiting. The line and the banners fade in and out, a banner with a slight pop, and under reduced motion they just show and go.
- **The Character window** (`packages/web/src/ui/characterWindow.ts`) is Diablo IV's. A mouse's has two tabs, Items and Stats. Items holds the doll, the purse, and the bag's 24 places. A finger's has three, Gear (the doll), Items (the purse and the bag), and Stats. The doll's places and the bag's are one size, and the doll is laid on the bag's columns (8 on a mouse, 6 on a finger, `COLUMNS` in `characterWindow.ts` and `--hud-columns` in `hud.css`): head, chest, hands, legs, and feet down the first column, the neck and the two rings down the last, the main and the off hand side by side under the body, and the player's live body (see "A portrait is the body itself") spanning the columns between. Each item is drawn at its slot or at its bag place, edged in its rarity's colour, the loot markers' (`RARITY_COLORS`). Stats (`characterStats.ts`) gives the whole totals as the rules read them from ranks and gear (`statsOf` and the rules over it): Pools, Offence, Defence with how often a Ghost's strikes land, Recovery, and Mending for a Healer or Warding for a Mystic, each line with where it comes from ("+20 ranks · +11 gear"). A total that changed since the tab last showed flashes gold. The window rebuilds only on a new inventory or lucidity.
- **An item in the Character window moves by press or by drag.** On a mouse, resting on an item shows its tip, with its icon and how to act on it. A double click or a right click wears an item from the bag, a ring in the free ring slot else ring 1, or puts a worn one away, which a full bag refuses with a line beside the slot. A single click does nothing. A finger's tap, and Enter on the keyboard, open the item's card, a dialog beside it with what its tip says and its buttons: Drop and Equip on a carried item, the Moonstone never dropped, and Unequip on a worn one, greyed out while the bag is full. The card is no `role="tooltip"`, since it holds a button and takes the pointer. A second press on the item, a press anywhere else, Escape, and closing the window close it. Either pointer drags an item (items take no browser touch gesture): from place to place, onto an occupied place swapping the two (`moveItem`); into a slot its base fits, which lights while the item is carried, both ring slots for a ring (`equip` with the slot); a worn item onto a bag place, put away there (`moveItem`); and out onto the world, throwing it toward where it is let go (`dropItem`, a worn one too, in one request whatever room the bag has). A slot the base does not fit refuses it: the ghost says which slot it goes in while over it, and on letting go the slot shakes beside a line saying so. A full bag refuses a worn item's way into the bag the same way: over a bag place whose item does not fit the worn item's slot, the place shows refused and the ghost says the bag is full, and on letting go the place shakes beside a line saying so. The Moonstone stays: over the world its ghost says so in place of Drop. The ghost and the letting go read one rule (`refusalAt`), so what the ghost refuses is what letting go refuses. The ghost follows the pointer at the offset it was taken at. Held over a tab for `TAB_SPRING_MS`, a carried item opens it, so a finger carries an item from Items to Gear.
- **A frame's bar shows a channel or a raise.** A thin bar hangs under a frame while its entity channels, named for the ability and draining in the Moonstone's light over the seconds left. While its entity lies fallen and is being raised, the bar shows the raise instead, filling in the gold of the raise's ring and named for the Healers holding on: under the target frame for a fallen target, and under the player's own frame while they are raised. Like a slot's sweep, the bar is a CSS animation timed from when it began, so it keeps its elements for the length of one channel, or of one `raising` snapshot. Each snapshot re-times it from as far as it says the raise has gone, filling on its schedule by a CSS `linear()` easing.
- **The chat is a pane, not a panel.** It lies bottom left as text. Its lines fade 8 s after the last one arrived or the pointer left them, and come back while the pointer rests where they lie. Enter, while the world has the keyboard and no control takes Enter itself, opens it with the field focused. Enter there sends the line, or with nothing typed sends nothing, and either way closes the chat and hands the keyboard back, so Shift runs again. Escape closes it too.
- **The HUD's art is the chrome's.** Everything is white line art over flat dark fills, at the 9-slice borders' 2px weight, with no gloss, glow, or gradient. A globe is a dark well in a 2px ring with a bracket arc outside it at the top and the bottom, filled flat from the bottom with a lighter line at the surface. A slot, a menu button, and a phone's round button show that they are on by a tinted plate and a second line just inside the edge, in the colour of what they do. The glyphs (`hudIcons.ts`) are Kenney's white CC0 icons from the pack's `UI/`, used as CSS masks over the control's ink (`.hud-glyph`), so one icon takes any colour. Where Kenney has nothing that fits, a glyph is drawn in `hudIcons.ts` as white SVG in the same weight: the chat balloon, the Moonstone, Cleave, Radiance, Dream-bolt, the fallen figure on a sensed marker, the elites' two traits, and the four people sigils. An effect shows the glyph of the ability that puts it on its holder, or of the elite's trait it is. Items are the one exception to the line art: an item in the Character window, its tip, its card, and a row of Mercus's panel is a coloured picture of its own model on a transparent ground (`ITEM_ICONS` in `itemIcons.ts`, from the pack's `UI/Items/`, see "Web asset pack"), inside an edge its rarity's colour draws.
- **The HUD has one tip of its own, not the browser's `title`.** `HUDTooltip` (`packages/web/src/ui/hudTooltip.ts`) is one panel in the chrome, over the part it explains, or under it where there is no room above, and inside the window. A part gets a tip through `setTip`, which also drops any `title`, since the browser's tooltip would show beside it a moment later. A mouse or a pen resting on a part shows its tip at once, unless a press held from the play field is under way, and leaving the part, a press, a scroll, or a resize puts it away. The pointer passes through it. It is `role="tooltip"`, and its part names it in `aria-describedby` while it shows. It reads its part again on every HUD tick and touches its elements only when what it says has changed, so a recovering pool does not rebuild it, and an effect's seconds count down in it. An ability's tip gives in red the first need the player misses, from `abilityRefusal` in `packages/core/src/abilities.ts`, the rule that greys the slot, so the two cannot disagree. It is not among `GameHUD.occluders`: it draws over the bubbles' canvas anyway, and only while the pointer rests on the HUD.
- **A portrait is the body itself.** Each frame's circle is left open in its plate, and after the world renders, `WorldScene.drawPortraits` draws the in-world body again in it on the same canvas, through an orthographic camera three-quarters in front of the body as it is turned (`packages/web/src/scene/portraits.ts`). It is not a clone, so it shows every clip the body plays in the same frame, and a fallen body is looked down on at its head bone. Its camera draws one layer, which the subject's model and the scene's lights carry and nothing else does, so no plaque, ring, prop, or ground shows, and the body's materials keep the programs the world compiled for them. A square with the circle cut out at the front of the depth range and a backdrop disc at the back clip the body to the circle, so the world drawn under the frame stays outside it. The backdrop is a light grey-violet behind the head, darkening to its rim, so a dark body such as a Ghost reads as a silhouette against it. The pass leaves the shadow maps and the scene's matrices as the world's render left them, and lifts only the hemisphere fill's intensity to a floor while it draws. The circles' rects are read once a frame, with the panels', so a frame lays the page out once. The Character window's body is a third portrait, `body`, on a layer of its own: the whole body three-quarters from the front (`bodyFraming`), over a backdrop that fills its rect, turned round it by a drag on it and a slow sway after the drag has rested 3.5 s (none under reduced motion), which turns this view alone. The window's plate leaves the body's rect open (`openBodyHole`, from the rect read with the others), and shows the hand models, since they hang under the model holder.
- **A coarse pointer gets a landscape layout** (`.hud--coarse` in `hud.css`, chosen once from `(pointer: coarse)` at startup). One strip runs along the top: the player's frame, with a small portrait and small Health and Spirit bars in place of the globes, then the target frame, then the clock and a ≡ that opens a sheet with Players, Character, Quest log, Settings, and the study line. The quest tracker stands flush right under the strip, under the ≡, folded to the quest that last moved, with "+N more" unfolding the rest and "Tap to fold" folding them again. It ends above the thumb's arc and scrolls past that, and gives way to a window and a carrier's panel. The line and the banner stand lower and smaller, clear of the strip, and wrap short of the tracker. Slot 1 is a big button under the right thumb, with slots 2–6 on an arc round it, Run at the arc's end, and the gaze lock beyond Run, a little higher. Balance is a thin bar at the bottom between the chat icon and Run. The chat hides behind an icon bottom left, its newest lines peeking above it and fading as on a mouse, and opens as a panel with a ✕. A window opens one at a time, as a panel down the right edge, low enough that its corner ✕ stays on the screen, and in turn with a carrier's panel, which stands there too. A finger has no hover, so a part held for 400 ms (`FINGER_HOLD_MS`, the hold that selects a body without walking) shows its tip until the finger lifts, and that press then presses nothing. A tap, or a hold that slides past `TAP_SLOP_PX` first, presses the part as usual. Closing the chat blurs its field on every device, so a phone's keyboard shows only while the chat is open. The edges keep clear of the safe-area insets. An upright phone (`UPRIGHT_PHONE_QUERY`: a coarse pointer, portrait, at most 600 px wide) is covered by a card asking to turn it sideways, which goes once it turns. That card is the only hold a browser tab has on orientation, since a manifest's orientation binds only an installed app. The canvas takes no browser touch gesture and no long-press menu.
- **A panel keeps its elements while its inputs are unchanged.** `AppShell.render` runs on every state change, and a recovering pool sends several `energy` frames a second. ## Web map editor

The map editor is a second Vite entry point (`packages/web/editor.html` + `packages/web/src/editor/**`) that authors `.somnio-sector` files — a development tool, not a shipped surface:

- **Dev-only by construction.** `editor.html` is deliberately never added to `build.rollupOptions.input`, so `vite build`'s default single input (`index.html`) keeps it out of `dist/` and therefore out of the image. `npm run build` machine-enforces this: `packages/web/scripts/assertEditorExcluded.mjs` runs after `vite build`, inside the image build too, and asserts `dist/editor.html` is absent and no editor marker (`__editor/sectors`, `somnioEditor`, `somnio-editor-root`) reaches `dist/bundle` or `dist/index.html`.
- **File I/O is a dev-server middleware** (`packages/web/vite.editorFs.ts`): a `configureServer`-only plugin serving `/__editor/sectors` (GET list, GET/PUT per percent-encoded stem, no DELETE), inert unless `SOMNIO_EDITOR_SECTORS_DIR` is set (the `editor` npm script sets it, defaulting to the repo-root `sectors/` staging directory; a dev server with `SOMNIO_SECTORS_DIR` pointed there plays what is being authored, and finished sectors are copied into `packages/core/fixtures/sectors`, the world the server image ships and the splash reel stages), loopback-only and same-origin-gated regardless of `--host`, path-contained against the realpath'd root, and atomic on write.
- **The sector codec** (`packages/core/src/sectorFile.ts`) is pinned byte-for-byte by the committed fixtures, each of which reads and writes back identical, so an authored save never rewrites unrelated bytes of a sector the server loads. The writer runs its output through the reader before returning it, so the editor cannot save a file the server would refuse.
- **The overlay shows what blocks.** The authoring overlay draws each placement's registry colliders along with walk surfaces, ledges, door triggers, and arrival points. A door and a fixture are the record kinds without a tool. A door is added from its placement's inspector at one of the model's anchors, and a fixture from the same inspector's Service picker, one to a placement, which None removes. Renaming a placement re-points its doors and fixtures, deleting it deletes them, and copying it carries them along under new ids.
- **The document is judged as `buildWorld` would judge it.** Every other sector in the directory is loaded on open, and `documentIssues` (`packages/web/src/editor/surroundings.ts`) runs `buildWorld` over all of them. The overlay marks each reported record in red, and `window.somnioEditor.issues()` lists them. What the rules need of named sectors (the inn's spawn, and every carrier, sector, and place a quest of `packages/core/data/quests.json` names, such as the Healers' trial's `NorthWood` and the Mystics' trial's three hidden places, each a point inside `WestMeadow`, `AutumnWood`, or `NorthMeadow`) is checked by the server alone, in `ruleSectorIssues`.
- **Neighbours are drawn read-only.** For an outdoor document the outdoor sectors touching it are drawn at their origins, so roads, walls, and tree lines can meet across a border.
- **Record labels are DOM elements** over the canvas, so `agent-browser snapshot` sees them.
- **English-only.** The editor renders literal English and never imports `@/i18n`, keeping `RENDERED_KEYS` and the catalog tests untouched.
- **It shares the client's chrome.** The editor loads `packages/web/src/ui/chrome.css` and builds its corner panels with the `packages/web/src/ui/dom.ts` helpers (`floating`, `floatingStack`, the panel and button builders). A change to either reaches the editor too, so check it there as well as in the game.
- The `/somnio-editor` skill covers serving and driving the editor with `agent-browser` (`window.somnioEditor` is its debug surface).

## Web asset pack

The browser reads glTF. `somnio-assets` carries `Web/Models/*.glb`, published by its `Pipeline/build-web-models.sh`, and `Web/Branding/` (the favicon, home-screen icon, and wordmark), written by its `Branding/scripts/export_web.py`. The panel textures and the HUD's icons live in that repo's root `UI/`. `Scripts/bundle-web-assets.sh` composes the served root from the three:

```
SOMNIO_ASSET_SOURCE=/path/to/somnio-assets \
SOMNIO_WEB_ASSET_DEST=packages/web/dist/assets \
  Scripts/bundle-web-assets.sh
```

The destination differs by consumer, and getting it wrong fails silently. `packages/web/dist/assets` is for the image build, where nginx serves `dist/`; the **dev server needs `packages/web/public/assets`**. Vite serves `packages/web/public` and `packages/web/`, never `dist/`, so a pack written to `dist` leaves every model and texture 404ing with a placeholder world and no error. `packages/web/public/assets` is gitignored and excluded from the Docker context, so a populated dev pack never leaks into an image.

`UI/` and `Web/Branding/` are required, because neither the chrome nor the brand has a fallback. Models only warn. The brand is served at `/assets/Branding/`. The script and CI's pack check both check its four files by name, and every `UI/` file the client loads (`UI_FILES` in the script), because a directory check passes a partial export. A missing icon would draw its control blank. `packages/web/test/ui-pack.test.ts` holds that list to the `/assets/UI/` URLs under `packages/web/src` and to CI's check. An icon added to the HUD therefore needs its file in `somnio-assets` first: that repo is pushed before the somnio commit that names the file, or CI's pack check fails.

`UI/Items/<baseId>.png` holds one picture per base item, which the HUD draws an item as (`itemIcons.ts`). The pipeline's `render_item_icons.py` renders each from the item's hand model, else its ground model, in three-quarter view at 128 px on a transparent ground, and gates the set. A new base item therefore needs its model registered and its picture rendered in `somnio-assets`, and the picture named in `UI_FILES` and CI's check, before the client names it.

The script additionally verifies **external resource sidecars**, both `buffers[]` and `images[]`, which is the whole surface glTF 2.0 declares external files on. Today's pack is entirely self-contained binary GLB, so the check finds nothing. It exists because a JSON glTF can point at a sibling `.bin` or `.png`, which three.js resolves relative to the model URL, so a pipeline change that started emitting one would serve a 404 for the model's geometry or its texture.

The served layout is `/assets/...` for the pack and `/bundle/...` for hashed build output (`build.assetsDir: 'bundle'`). They must not share a directory — the client references the pack by absolute URL.

Prop models (the registry's `objectModels` stems, empty `expectedClips`) are **placement-normalized before export**: local origin at the ground-footprint center, long horizontal axis along X. The runtime adds no per-object scale and puts each clone's origin at its placement's `x`/`z`, turned by `yaw`. Collision never measures a loaded model: it comes from the registry's `footprint` and `colliders`, so an un-normalized prop draws shifted or mis-sized against what it blocks. The pipeline's footprint gate holds each written model's ground bounds to its registry `footprint`. The pipeline's sizing modes and authoring conventions live in that repo's `CLAUDE.md`.

Hand models (the registry's `handModels` stems) are not placement-normalized. Each is exported in the frame of the KayKit `handslot` bone it is held on, its grip at the origin, and the scene hangs a clone at identity under that bone of the dreamer's model: `handslotr` for the main hand and `handslotl` for the off hand, as `GLTFLoader` names `handslot.r` and `handslot.l`. The characters themselves export unarmed. The pipeline's hand-prop gate holds each written hand model static and at its grip.

Ground models (the registry's `groundModels` stems) are what a drop lies on the ground as, one for every item that can drop. They are placement-normalized like props, but lying: the lowest point on the ground plane, the ground bounds centred on the origin, and the size a dreamer holds or wears the item. The scene puts a clone's origin at the drop's point, turned by the drop's own yaw, and never measures it. A weapon's, a shield's, and a focus's come from the same KayKit piece as their hand model, laid flat. The pipeline's ground-item gate holds each written ground model static, on the ground, centred, and no bigger than a held item.

## Hosting

`packages/web/Dockerfile` builds `ghcr.io/tobihagemann/somnio-web` from a **repository-root** context (the workspace symlinks resolve through the root `node_modules`, and the asset pack is at `assets/`). It requires `--build-arg BUILD_VERSION` like the server image, and greps the bundle for the marked stamp `somnio-web <version>` to prove the version was injected — see `packages/web/src/buildInfo.ts` for why the stamp interpolates the define directly rather than reusing the exported constant.

There are no releases, version numbers, tags, or changelog. The `publish` job in `ci.yml` builds both images from every commit on `main` that passes the other four jobs and pushes them as `ghcr.io/tobihagemann/somnio-server` and `somnio-web`, each tagged `sha-<short>` and `latest`. `BUILD_VERSION` is that short sha, so the admin `version` verb and the `somnio-web <version>` stamp name the exact commit a container runs. The deployment runs `latest` for both images and redeploys whenever any service in its stack changes, so any green commit on `main` can go live at any moment: a change that breaks the wire must bump `helloVersion` in the same commit (registry geometry counts, see "Wire protocol"), and the committed sector fixtures are the live world.

The static image does **not** proxy `/ws`; whatever fronts it performs the split (the `proxy` service in `docker-compose.example.yml` locally, Traefik in production), which is what lets the client's origin-relative `wss://<host>/ws` resolve with no dev-only branch.
