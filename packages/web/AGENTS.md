# Browser client (`packages/web/`)

The instructions are split by package, and a section named in a "see ..." lives in one of these files:

- `AGENTS.md` (repository root): tech stack, package graph, build and test, logging, deployment, lint and format, code conventions, localization.
- `packages/protocol/AGENTS.md`: the wire protocol's framing, the pre-login limit, characters, joining, interest, what others see of a dreamer, and what breaks the wire.
- `packages/core/AGENTS.md`: the gameplay rules and their frames (movement, doors, acting, abilities, threat, elites, bosses, gear, trading, drops, speech, pools, raising, fixtures, lucidity, quests, the bounty board), the sector format, and the model registry.
- `packages/web/AGENTS.md`: the browser client, the frame budget, the web map editor, the web asset pack, and hosting.

A Three.js client that speaks the wire protocol through the shared `@somnio/protocol` package.

```
npm run dev --workspace packages/web      # Vite on :17669, proxying /ws to the local server on :17662
npm run editor --workspace packages/web   # Vite with the editor entry + sector file API (see "Web map editor")
npm run conformance                       # wire conformance against a LIVE server (SOMNIO_CONFORMANCE_URL)
```

## What holds the client and server together

The protocol and core packages are shared code, so the two sides cannot disagree about a message shape. They also run the same movement rule (`packages/core/src/collision.ts`) over the same sectors and the same registry geometry. Two suites guard the parts that are not shared:

- **Golden frames** (`packages/protocol/fixtures/golden-frames.json`) are compared as canonicalized JSON (object keys sorted) by `golden-frames.test.ts`. This is the check that catches a payload **property rename** — the round-trip suites encode and decode with the same renamed property and stay green. Re-record deliberately with `SOMNIO_RECORD_GOLDEN_FRAMES=1 npx vitest run --project protocol`.
- **Wire conformance** (`packages/web/test/conformance/`) drives the real TypeScript encoder and transport into a real server. Its outbound case is what proves application frames ship as **text**; everything else in that file passes while the transport sends binary. The over-cap frame case accepts either close code in `[1009, 1006]`: the client is still writing a ~1 MiB payload when the server refuses it, so whether the close frame arrives before the reset is transport timing.

## Browser-only decisions

- **Session tokens.** A browser page needs a refresh to survive, so the server issues a resumable token on `Login.requestSessionToken` and accepts `redeemSession`/`revokeSession`/`revokeOtherSessions`. Issuance is **request-gated** on that optional field: a connection that neither asks for a token nor redeems one never receives a `sessionToken` frame. `revokeOtherSessions` is the game menu's Log Out Other Browsers, answered `otherSessionsRevoked` with the count of the other unexpired rows it ended. It deletes every row of the account, including the one for the token this connection redeemed or was issued, so a copy someone took of this browser's token ends with the rest. When that row was live, a fresh token with the same expiry replaces it in the same transaction and reaches this browser as a `sessionToken` before the answer. The client saves it over the token its connection holds. That includes a resumed session's token, which has no `rememberMe` to gate the save on. It never saves over a token another tab has since stored. Unlike `revokeSession`, the action leaves this browser logged in and in the world. A login or a session redeem reports `otherSessions {count}`, the account's other unexpired rows. A copy shares this browser's row, so no count shows it. So the menu offers the action on every connection that holds a token, and elsewhere only while that count is above 0. One account has one live connection, so no other browser can add a row while this one plays. The count can therefore only fall until the next login or redeem.
- **DOM UI over WebGL.** Panels and overlays are real elements, so password managers work and `agent-browser snapshot` sees them. `packages/web/src/ui/chrome.css` draws the Kenney 9-slice chrome with `border-image-slice: 36` against an 18px border — the slice is unitless _image pixels_.
- **The orthographic camera's `scale` is a vertical HALF-height**, so the Three.js mapping is `top/bottom = ±scale`, `left/right = ±scale × aspect`. The usual `frustumSize / 2` idiom halves it again and renders the whole world at 2x. The game's default is 7, 14 m shown top to bottom (`ORTHO_RIG` in `packages/web/src/scene/cameraRig.ts`). The player zooms by the wheel or a pinch between 0.78 and 1.4 times that (`PLAYER_ZOOM`), a half-height from 5 m to about 9 m. The editor keeps a zoom range of its own (`EDITOR_ZOOM`).
- **Resize holds the vertical world extent constant.** A gameplay contract, not a rendering detail: a bigger window magnifies rather than reveals. Name plaques and speech bubbles are sized in metres too, but never drawn smaller than 1.2 CSS pixels per pixel of their art (`OVERLAY_MIN_SCREEN_PIXELS` in `overlayArt.ts`), so their text stays readable on a small window or a phone.
- **The ground is painted, not textured.** Each sector's ground is one plane whose shader draws every floor material from a procedural recipe (`packages/web/src/scene/groundMaterials.ts`, the one list of floor-material ids) by two weight textures. `groundField.ts` computes those weights from the sector's background, its touching outdoor neighbours' backgrounds (blended over 5 m in noisy patches), and the marks of all of them. One field takes tens of milliseconds, so `groundRasterizer.ts` runs it in a module worker, and inline where there is no worker or the worker fails. Two touching sectors of one texel size (every sector up to 81.92 m across) compute identical weights wherever both rasterize, so their seam cannot show: every input is keyed to space position, marks paint in one order (sector name, then index), and a sector's raster carries a gutter past its edge. The scene keeps drawing a sector's previous field until the next arrives, and paints the player's own sector on the spot before revealing a new space. What grows on a sector's ground, its tufts, pebbles, and flowers, takes milliseconds a sector to place, so `scatterer.ts` places it in a module worker as well, and inline where there is none. A border crossing makes several sectors due at once, so one is sent a frame, nearest the camera first. A sector's last scatter stays drawn until the next is placed. The player's own sector's scatter is placed on the spot with its ground before a new space is revealed, so the floor never appears bare. The ground draws after every other opaque mesh, so its costly shader runs only where nothing stands in front of it. The grass leans away from what touches it and springs back once let go (`grassSpring.ts`): a body's feet and lower legs, and whatever its hands hold, along the item's length wherever it dips into the grass.
- **A press on the play field acts, walks, steers, picks up, or uses.** A mouse, a finger, and a pen take one path, the primary button only, but for a press on a body (see "One target"). The scene picks by shape what is drawn under the pointer (`WorldScene.pressTargetAt`): first a drop's name, then an entity's body (`WorldScene.entityAt`, a capsule from feet to head, the one the pointer's ray enters first), then a drop's model as it lies, a little round it (wider under a finger), then a fixture's model (`WorldScene.fixtureAt`, the meshes of the placement that carries it as they are drawn, nearest the camera first), then the ground (`WorldScene.groundPointAt`, which meets the top of a walk surface before the floor beyond it). A body's capsule reaches as far across the ground as its model does in its idle pose, measured as the model is put in, so a press on a wolf's snout or tail picks it. It is never narrower than the body's radius, and at least 0.6 m on a coarse pointer. A body is picked down to its feet, so it covers a drop's model under it. The drop's name stands under its model on screen, below the feet of a body on the drop, so the name is what reaches a drop under a body. A press on a drop walks the player into `PICKUP_REACH` of it and picks it up (see "Drops"). A press on a fixture walks the player into speaking distance of its placement's centre and uses it, at once from within that distance (see "Fixtures and services"). A fixture's model is picked rather than its footprint, because the camera looks down on a tall board and a ray through its face meets the ground about a metre beyond it. A right press on a drop or a fixture does nothing. A press on a body walks the player to it and acts there (see "One target"). The player's own body is no part of the pick, since their own frame is how they target themselves: a press there lands on what lies under it, a drop's model or the ground. A press on the ground keeps the target. Up within 180 ms and 12 px of where it landed (`HOLD_TO_STEER_MS`, `TAP_SLOP_PX`), it is a tap, which walks to where it landed. Held longer or moved further, it steers toward the ground under the pointer, and on coming up walks on to where it came up. A second pointer down makes it a pinch, which zooms and walks nowhere until every pointer is up.
- **One target.** A left press on a body (`GameplaySession.pressEntity`) makes it the target, which a ring marks. On an NPC it walks the player up beside it. On the way it asks the NPC to go on (`interact`) the first time they stand within speaking distance, which opens its panel when it carries a service, or while its quest marker shows (see "Fixtures and services"). So an NPC behind a counter is still asked, from as near as the player gets. On a body slot 1 can act on (`engageAction`), it holds the player's facing on it (see below), switches slot 1 on, sending `engage` after `target`, and walks the player up beside it. That walk ends in touch (`reachDistance` in `combat.ts`), which is Attack's reach and a raise's, and lies within Mend's. A Healer who would mend from further off selects the dreamer without walking (a right press, or a finger's rest) and switches slot 1 on with its button or the 1 key. On another dreamer slot 1 cannot act on, it walks the player up beside them all the same. Any other body, such as a nightmare while a quest held forbids striking, it only selects. The walk follows the body, aimed at it again whenever it has moved `FOLLOW_REAIM_METRES` (0.5 m) from where the walk heads, and ends the first time the player stands in range of where the body stands then. A body that moves away after that is not followed, and a nightmare driven off before then stops the walk where the player stands. The press ring drops on the body, moves with it, and lifts as the walk ends, as it does on a fixture or a drop a press walks the player to. From within range already, the walk under way stops and the press acts at once, with no ring. A press on the ground ends the following, and another target stops its walk. A right press on a body (`GameplaySession.selectEntity`), the same pick, only makes it the target, without walking, and slot 1 stays on where it can act on the new target, as at any change of target. A right press on the ground, the ground under the player's own body included, clears the target and the queue behind it. A nightmare driven off is nothing to act on while it lies: a press passes through it, and a player whose target it was is left with none as it falls (`onEntityReset`), unless a nightmare lined up behind it is taken up (see "Shift lines nightmares up"). A nightmare's `blow` at a player who has nothing targeted, stands still, and can act makes that nightmare their target (`GameplaySession.answerStrike`), so a player struck fights back without finding the attacker. Standing still means no walk under way, no press held, no body being walked up to, and no door being taken. The strike holds their facing on it and switches slot 1 on where it can act. The first blow wins. A player walking or steering is left as they are, so a strike never turns someone fleeing. A finger and a pen have no right press, so they rest on a body instead: lifted within `FINGER_HOLD_MS` (400 ms) of landing, a press on a body acts as a left press does, and resting that long it only selects. Sliding past `TAP_SLOP_PX` first, it steers as a press on the ground does. A mouse's left press acts as the button goes down. A press on a dreamer's name in the Players window also makes them the target. A press on the player's own frame, or on their own name in the Players window, makes them their own target, and the target frame reads their health from their own `energy`. The ✕ on the target frame clears the target and the queue behind it. Escape takes one thing away at a time: the open chat, then a finger's menu sheet, then an item carried in the Character window, then an item's card, then the newest open window, then a carrier's panel, then the walk under way, which stops where the player stands (`GameplaySession.stopWalk`, though a leap runs on, and a press held on the ground, the player walking on purpose, steers on, Escape passing over it to the target), then the target with the queue behind it, and only then does it open the game menu. While the loading cover stands (see "A cold entry is covered until the player is dressed"), Escape skips every one of these and opens the game menu over the cover, so what the cover hides stays as it is. What stands open goes before the walk, since it is what the player means to put away.
- **The gaze lock.** The player's facing is held unless they free it (see "Movement" in `packages/core/AGENTS.md`). Held, they face their target, any body targeted but themselves, in view and not driven off, walking or standing, so a Fighter backs away still facing the nightmare, at half pace. With no target they face the way they walk and keep their facing once they stop. The target's ring shows the lock and slot 1 together: green while slot 1 is off and gold while it acts, a plain ring while the player does not face the target and a reticle with four ticks pointing in while they do (`GameplaySession.gazeLocked`). The target frame's accessible name says the lock. The 1 key switches slot 1 alone, so a lock with slot 1 off is a green reticle. The gaze lock's own button (`GazeLockButton` in `belt.ts`) stands before Run on the belt, and beyond Run on a finger's layout. Its key is F (`GAZE_LOCK_KEY`), under the same gates as the belt's other keys. It frees the facing or holds it again (`GameplaySession.toggleGazeLock`, `facingFree`), a fallen player's too. It leaves the target and slot 1 as they are, so a Healer mends on while facing the cursor. Freed, the player faces the cursor on a mouse, walking and standing, even with a target, and the way they walk on a finger. What the cursor points at is picked only while freed on a mouse (`WorldScene.cursorFacingAt`): another body's feet, else the ground point a press there would steer to. Over the player's own body, nearer the camera than any body behind it, it is nothing, so they face the way they walk. A freed facing lasts through doors, until a left press on a body slot 1 can act on, a strike that targets the player, or the queue taking up its next nightmare holds it again. The button is always enabled, with nothing targeted too, since what it holds decides how the next target is faced. It is drawn as the target's ring, and pressed and lit as the reticle while the facing is held.
- **Shift lines nightmares up behind the target.** On a mouse, Shift with a left press on a nightmare slot 1 could attack queues it behind the target (`GameplaySession.queueEntity`). On one queued already it takes it off the queue, on the target it does nothing, and with no target it acts as a plain press. With a target, Shift on a nightmare slot 1 cannot attack does nothing. Shift on anything but a nightmare (another body, the ground, a drop, or a fixture) does what a plain press does. A finger and a pen have no Shift, so they queue nothing. A body made the target by any press leaves the queue, so a target is never in its own queue. When the target is driven off or leaves view, the first nightmare still queued that slot 1 can attack becomes the target in the same frame, as a left press takes it: its facing held and slot 1 on, walked to unless a press held on the ground keeps steering (`advanceQueue`). Where the player cannot act then, under an overlay or fallen, or is taking a door, the queue is cleared instead, so a queue never stands without a target. A queued nightmare drops out as it leaves view or is driven off, and on the next tick once slot 1 can no longer attack it, as when a quest that forbids striking is taken on. Clearing the target (Escape at its step, the ✕, a right press on the ground), a plain left press on another body, a fall, and a new space clear the queue. Walking, steering, and a right press on a body keep it. Each queued nightmare has a faint ring at its feet, in the target ring's colour, green or gold as slot 1 is off or on, at 40% of its opacity (`QUEUE_RING_OPACITY_SHARE`). One dotted trail runs on the ground from the target through the queue in order, kept clear of every ring, its dots lying on whatever floor or tread is under them (`WorldScene.showQueue`). The queue costs one draw call per queued ring and one for the trail, which hangs on the scene only while it has dots. It adds no program, since the trail draws with the rings' settings.
- **Slot 1 acts on the target.** It is one toggle, the first slot of the HUD's belt (the big button under the right thumb on a finger's layout) or the 1 key, and a left press on a body switches it on too (see "One target"). What it does there, and when it goes on and off, is `engageAction` in `packages/core/src/combat.ts` and the `engage` rules (see "Acting"), applied alike on both sides. The button is named and drawn for that action, Raise where Mend meets a fallen dreamer. It is lit while on, and the target's ring is gold. At anything else it is greyed out and keeps its last look, so a Healer who puts the Moonstone away finds it greyed out at a dreamer. At a nightmare it cannot attack, it is Attack, greyed out, and its tip says why in red: something in the main hand that does not swing, or a quest held that forbids striking. That is `attackRefusal` in `combat.ts`, the rule `engageAction` reads, so the tip and the slot cannot disagree. The slot and the 1 key never walk the player toward the target. Only a left press on it does, and the queue as it takes the target up. The client slows its own player when a `blow` names them as the attacker, since the server chooses the moment of each swing.
- **Slots 2–6 use abilities.** They hold the abilities the player's ranks teach, in the order of the teachings that teach them (`abilitiesTaught` in `packages/core/src/abilities.ts`), and empty slots after them. A press on one, or the keys 2–6 under the same gates as the 1 key, uses it (see "Abilities and effects"). A slot is greyed out while `abilityRefusal` names a need the player misses (the rule `abilityAllowed` applies), and swept dark while a cooldown runs, its own or the global one, whichever ends later. Its own counts down in whole seconds; the global one only sweeps. The sweep is a CSS animation timed from when the `cooldowns` frame says the cooldown began, so a slot keeps its elements across `energy` frames. How long a cooldown runs in all comes from its rank and the set worn as it starts, and a later frame moves only its end (see "Gear" in `packages/core/AGENTS.md`). A slot's tip gives its cooldown and channel the same way, by the rank held and the set worn (`AbilitySlotState`), so Lunge reads a third shorter in the Fighters' six pieces. Run is drawn held off, and described so, while an effect keeps the player from running.
- **The HUD** (`packages/web/src/ui/hud.ts`, styled by `hud.css`, which the editor does not load). The player's own frame sits top left: their portrait in a ring of their condition, their name, and their people and role. The people comes from each `enterSpace`, so a resume straight into the world draws it too. The target frame sits top centre with the target's portrait. Each frame carries a row of the effects its entity holds, from the `effects` frames: a glyph per effect with its whole seconds left, which keeps its element while the effect holds. The world clock sits top right, as `☾ 22:40` or `☀ 14:05` with the sector's place name (`placeNames.ts`). The client runs the clock on from `enterSpace` (`ConnectionController.worldSecondsAt`), and the sun is up from 6 to 22 (`sunIsUp` in `packages/core/src/worldClock.ts`), which the world's light and a night-only door read too. The belt sits bottom centre: a Health globe and a Spirit globe filled by the exact pools, a Balance arc across its top that turns orange under a Winded tag, slot 1, slots 2–6 for abilities, the gaze lock and Run at its end, and one line saying what the player studies and how far toward the next rank. A globe shows its number and its word only while the pointer rests on it, since its fill already says how full the pool is. Players, Character, Quest log, and Settings sit beside the Spirit globe. The first three open windows, several at once with the newest on top, the Players window and the Quest log beside the Character window while it is open; Settings is the game menu. While a carrier's panel is open down the right edge, every window stands to its left (`GameHUD.setCarrierPanelOpen`), so neither hides the other. In a window too narrow to hold the Character window beside the panel (`windowsBesideCarrierPanel`, 760 px), a window and the panel take turns, as on a finger: the panel opening closes the windows, and a window opening closes the panel. The Character window at Mercus's shop is the exception (see "A carrier's panel is not an overlay"). The HUD tells the shell of each window it opens and closes (`onWindowOpened`, `onWindowClosed`), and the shell decides what that does to the panel. C and I also open and close the Character window, O the Players window, and L the Quest log, under the same gates as the belt's keys, so not while the chat has the keyboard. None of these keys, the belt's included, acts with Alt, Ctrl, or Cmd held, since those presses are the browser's or the system's. Alt+Enter enters and leaves fullscreen, since the browser keeps F11 for its own. It is the page's key rather than the world's, so it works under an overlay too, though not while the chat has the keyboard, and the Options overlay names it over its Fullscreen button. Each window's menu button names its first key in its tip (`WINDOW_KEYS`). A window's title stands alone in its row, centred over the window, and its ✕ is a small chrome button on the panel's top-right corner (`windowHead` in `hudWindows.ts`, which the finger's chat panel uses too), named "Close" and the window's title. Speech bubbles keep clear of every HUD part that shows (`GameHUD.occluders`), the faded chat excepted. On a mouse, in a window too narrow or too short for it, the HUD shrinks evenly (`GameHUD.setViewport`): the frames, the clock, the quest tracker, the line and the banner, and the belt scale toward the edges they stand at, so each stays whole and none overlaps another. A window keeps its width and ends above the menu.
- **The quest tracker, the line, and the banner.** The quest tracker sits under the clock while the player holds a quest (`questTracker.ts`): at most three quests held (`TRACKER_SHOWN`): those that moved most recently, the latest first, a quest newly taken on included, then others in the log's order. Each has its title and each objective line, its full stop giving way to its count ("Visit Mercus in his shop: 0/1", `objectiveCount` in `questText.ts`), a met line in the markers' grey, a quest done by its title and where to return, in the markers' gold, and a bounty how long it has left ("Runs out in 5 h"). Past those three, "+N more" opens the Quest log. Its heading, the Quest log's glyph and "Quests", is a button that hides and shows the list, named for which it does, with the quests held against the log's room beside it ("4/10"). The choice is kept per browser in `localStorage`. A bounty's time left, here and in the Quest log, moves with time rather than with a frame: `GameHUD.tick` says it each frame from an injected epoch clock (`wallNow`), touching a line only when its text changes. It is whole hours, and under an hour whole minutes, both rounded down, and stays at "0 min" until the server's `quests` frame drops the bounty. The tracker does not show while the Quest log is open. While a carrier's panel or a window is open down the right edge, it stands to the left of them where there is room beside the target frame, and else hides (`GameHUD.placeTracker`). Under the target frame, a line says each line of a quest held whose count moved ("Drive off 4 Skeletons in the Graveyard: 2/4", the count in the markers' gold) for 3.2 s, and a newer count replaces it and starts it over. A quest done is a banner there instead, "<title> complete" in gold between the window titles' divider flanks and where to return under it, for 4.5 s, cutting a line short (`questFeedback.ts`). A quest turned in is a banner the same way: its title in gold, then what it granted and paid in one line ("60c · 30 practice toward Toughening", a trial's "You are a Healer · Touch, rank 1", a gate's "Follow-through, rank 1"), then each item it gave by name in its rarity's colour on a line of its own (`turnInSaid` in `questText.ts`). A quest taken on is a banner the same way, one for each quest a frame adds to those held: a small "Quest accepted" over its title, both in gold, then what it asks a line each, as `objectiveLines` says it, the hidden places as one line (`acceptedSaid`). It is said nowhere else, in no count and no chat line, however far the quest has come as it is taken on. A quest shared with the player is also said in chat (see "A quest shared with the player shows a prompt"). One shows at a time. A banner arriving while another shows waits its turn. A count waits behind every banner, and the newest replaces any count that waits. Both come from the session's `onQuestNews`, from the `quests` frames after the baseline, as the chat lines do. A turn-in pairs the frames that answer it into one piece of news. The `quests` frame that moves a quest held to `done` opens it. When the quest pays coins or an item, a trial's Moonstone or wand included, it waits for the `inventory` frame the server sends last, and takes that frame's coins gained and `rewarded` (`GameplaySession.announceTurnIn`). Whether it waits, and what it teaches, follow from the quest by `turnInGrant` in `packages/core/src/quests.ts`, the rule the server's turn-in reads too. Its practice goes toward the teaching studied as the `quests` frame arrives, so the `lucidity` frames between add nothing it needs. A join drops a turn-in still waiting. The line and the banners fade in and out, a banner with a slight pop, and under reduced motion they just show and go.
- **The Character window** (`packages/web/src/ui/characterWindow.ts`) is Diablo IV's. A mouse's has two tabs, Items and Stats. Items holds the doll, the purse, and the bag's 24 places. A finger's has three, Gear (the doll), Items (the purse and the bag), and Stats. The doll's places and the bag's are one size, and the doll is laid on the bag's columns (8 on a mouse, 6 on a finger, `COLUMNS` in `characterWindow.ts` and `--hud-columns` in `hud.css`): head, shoulders, chest, legs, and feet down the first column in the body's order, the neck, the hands, and the two bracelets down the last, the main and the off hand side by side under the body, and the player's live body (see "A portrait is the body itself") spanning the columns between. In a window too short for it, a tab's page scrolls inside the window. Each item is drawn at its slot or at its bag place, edged in its rarity's colour, the loot markers' (`RARITY_COLORS`). Stats (`characterStats.ts`) gives the whole totals as the rules read them from ranks and gear (`statsOf` and the rules over it): Pools, Offence, Defence with how often a Ghost's strikes land, Recovery, and Mending for a Healer or Warding for a Mystic, each line with where it comes from ("+20 ranks · +11 gear"). Ward strength holds the Mystics' set's share too (`wardShare`). A dreamer wearing any of their role's set also gets the set's group, "Healers' set (2/6)", counting at most six, with each step in effect, none until two (`setBonusesOf`). A total that changed since the tab last showed flashes gold. The window rebuilds only on a new inventory or lucidity, or as the shop opens, closes, or locks its trades. An item's tip (`itemTip` in `itemText.ts`) gives one line per stat, the base's own and every rolled line of it added together by `itemStats`, the rule `statsOf` reads. A weapon's rolled damage is folded into its swing line (`swingFor`). Its title is the item's name, after its strongest roll for an uncommon or rare one (`itemTitle`), which the item's accessible name and its card's say too. Every item but the Moonstone says what Mercus pays for it ("Sells for 75c"), in the field as at his shop. A set piece's tip says after its rarity and slot who alone can wear it ("Healers only"), in the warning's red for a reader of another role or none, and gives its set under its stat lines, before what Mercus pays: "Healers' set (n/6)", n the pieces of that line the reader wears, at most six, then its three steps, "(2) Renewal lasts 4 s longer." and so on, each lit once the reader is of the line and wears enough for it, and dimmed otherwise.
- **An item in the Character window moves by press or by drag.** On a mouse, resting on an item shows its tip, with its icon and how to act on it. A double click or a right click wears an item from the bag, a bracelet in the free bracelet slot, else the first, or puts a worn one away, which a full bag refuses with a line beside the slot. While Mercus's shop is open, even with the Character window in his panel's place, a double click or a right click on a bag item he buys sells it instead, as its tip says. While a trade holds the lock it does nothing. A single click does nothing. A finger's tap, and Enter on the keyboard, open the item's card, a dialog beside it with what its tip says and its buttons: Drop and Equip on a carried item, the Moonstone never dropped, Sell at the shop ("Sell for 15c", greyed out while a trade holds the lock), and Unequip on a worn one, greyed out while the bag is full. The card is no `role="tooltip"`, since it holds a button and takes the pointer. It stands no taller than the window, and what it says scrolls above its buttons, which stay in view, as on a phone on its side. Opened again on the same item, as a new inventory reopens it, it keeps where that was scrolled to. A second press on the item, a press anywhere else, Escape, and closing the window close it. - **One-shot clips have no fallback.** The fall, a swing, a flinch, a throw (see "Drops"), and each ability's clip, played from its `ability` frame (`ONE_SHOT_CLIPS` in `packages/web/src/scene/animation.ts`), are events, not poses, so a model without the clip keeps its looping pose. A dreamer's swing is the blade slice, `Melee_1H_Attack_Slice_Horizontal`, which Cleave and every skeleton play too, and a Ghost's and each beast's is its punch. A boss's wail plays the long cast, `Ranged_Magic_Spellcasting_Long`, from its `telegraph` frame, and its call to its minions `Ranged_Magic_Summon`, from a minion's arriving `entity` frame. A body that already lies fallen as its model is put in, whether it comes into view lying or its model is swapped, lies at the fall's last frame and never falls again (`layFallen`). Only a change to fallen in view plays the fall from its start, so a body whose fall still waits for its blow falls when the blow lands.
- **Speeds are set for play, not by the clips.** Every figure, dreamers included, moves two to seven times faster than its walk or run clip's planted feet would carry it at `CHARACTER_SCALE`, and the client never time-stretches a clip to make up the difference (`CLIP_PREFERENCES` in `packages/web/src/scene/animation.ts`). Matching a body's speed to its clip's stride would leave a nightmare unable to catch a jogging dreamer, so choose a movement speed for play and let the feet slide. A nightmare plays its walk clip on the `walk` gait and its run clip on `run` (`movementPose`; see "Threat" in `packages/core/AGENTS.md` for when it sends each). The run clip is `Running_A`, or the Ghost's `Fast_Flying`. The Ghost has no walk clip and strolls on `Flying_Idle`.
- **Combat effects land with the clip.** `packages/web/src/scene/combatEffects.ts` draws them from the `blow`, `ability`, `effects`, `mend`, `raising`, and `telegraph` frames, a minion's arriving `entity` frame, and its `leave` carrying `crumbled`, and sends nothing. That includes the word over a body a blow missed, a mend's light, and a raise's ring. The miss word is bare outlined text at the plaques' size, so it never reads as a name plaque. It rises from the head, easing out over its 0.8 s, and fades out over the last 0.35 s of them. Under reduced motion it holds still and whole. A nightmare that evades a blow, a Dream-bolt, a Weaken, or a Bind (`evaded`, see "Threat") shows "evaded" ("ausgewichen") the same way in its place, from a pool of its own. A `blow` plays the attacker's swing and lands when its blade or fist does (`STRIKE_AT`, shares measured off the clips' hand bones; an unlisted clip lands at once). A dreamer's swing draws a white line-art arc round the target, hit or miss, with no depth test, so a body in front cannot hide it. A hit flinches, flashes, staggers, and sparks the target, and holds the two bodies' clips for about 60 ms. The server sends the blow that fells a body before its fall, so the body's fall waits for the last hit on its way to it (`CombatEffects.hitsLandIn`). It starts as that hit lands, in place of its flinch, in the frame a nightmare's drops burst out (see "Drops"). With none on its way, as after a Dream-bolt or a wail, and under reduced motion, it starts at once. Only the clip waits: the `condition`, its plaque, and every rule that reads it change as the frame arrives. The camera shakes, as an offset over where the rig puts it, only for a blow that names the player. The server sends a Cleave's blows straight after its `ability` frame, so the caster's first blow at each body within 100 ms is the Cleave's and lands as the sweep passes that body; a second at the same body is slot 1's. Challenge marks the nightmares within its range, as they are drawn, with a "!" and a pulse at their feet. Brace outlines the dreamer, Lunge trails the leap and bursts on contact, and Rally lifts the dreamers its wave reaches. The Healer's looks are in the Moonstone's pale light, a raise's in gold, and the Mystic's in one dream violet. Rising light is kept for heals and lifts, so Dream-bolt is drawn as harm, in a harsher violet. A raise's ring fills from the side of the body away from the camera, over a faint whole ring. Three looks keep the server's timing. Deep mend's long cast is started part-way in, so the Healer's push falls at the channel's end. It bursts at the recipient on `done` and puffs out at the Healer on `broken`. A Dream-bolt's shard arrives as the server lands its harm (`boltFlightSeconds`), and one its nightmare evaded flies all the same and shows the evaded word there. A Weaken or a Bind its nightmare evaded flicks to it all the same and shows the evaded word where the curse would take hold. A Ward's shell loses a facet with each blow it takes and flies apart as the blow that spent it lands. A boss's telegraph is a red circle on the ground where the frame puts it: faint to its rim, filling from its centre to its rim as its seconds run, its rim beating faster as the strike nears, and flaring as it strikes. One told of part-way shows as full as `TELEGRAPHS` says it is, and the caster's long cast is started so its push falls as it strikes. A circle ends unstruck, with no flare, once its caster is driven off or gone. A minion a boss calls up arrives in a ring of pale green grave light swelling from its feet, with motes rising round it, as the boss plays its call, since no clip raises it from the ground. One that crumbles never plays the fall: its arrival runs backwards, the ring closing in on its feet as motes rise where it stood. Its body, its plaque taken off and no longer an entity of the scene, sinks into the ground over `CRUMBLE_SECONDS` (0.9 s) and is then removed (`WorldScene.crumbleEntity`). Any other nightmare whose `leave` comes without `crumbled`, its lie over, out of view, or gone from the space standing, fades from opaque to clear where it is over `BODY_FADE_SECONDS` (1.5 s), playing on as it goes, and is then removed (`WorldScene.fadeEntity`). It is no longer an entity of the scene, and draws with clones of its materials (`fadeOut`), so no other body of its kind changes. The programs those clones draw with compile in `WorldScene.prewarm` once the models are loaded. A fading body stops casting its shadow halfway out, since three draws a shadow whole whatever the opacity. Under reduced motion a circle's rim holds steady and it strikes with no flare, though it still fills, a minion's ring fades where it stands with no mote rising, and a crumbling or fading body is gone at once. A mark, an outline, a shell, or a binding lasts its effect's rank-1 seconds (`EFFECTS`), or as long as `effects` says for the player and their target. Under reduced motion nothing shakes, holds, staggers, or lifts. Every mesh comes from a pool of fixed size (`EFFECT_POOL_SIZES`), and a body's flash and outline are built for its model with the materials of those dropped. Each kind draws with clones of one material, so its program compiles once, in `WorldScene.prewarm` before any of it draws, and no effect adds a light. A brief one takes the oldest of its pool once all are in use. What lasts as long as the server says (a mark, a channel's beam, a raise's ring, a shell, a binding, a telegraph's circle) waits for a free one rather than taking another's. The effects hang on a root of their own and draw over a body through its skeleton from there, never from a model holder, so no portrait shows them.
- **A stalled tab drops the combat effects in flight.** Once no frame has been drawn for 1.5 s (`STALE_EFFECT_MS`), as in a hidden tab, nothing queued or under way plays on its return. Until a frame is drawn again, no `blow`, `ability`, or `mend` starts anything, so the queue stays bounded while the tab is hidden. A channel's landing or break still ends its look, since that is the server's state. The effects' clock catches up by the stall, so a look that lasts as long as the server says (a mark, an outline, a shell, a binding) is gone on return if its time ran out meanwhile, and shows on if it still runs. A raise's ring and a telegraph's circle run on wall time rather than the effects' clock, which a slow frame holds back. On return a circle is gone if its time ran out and shows on otherwise, and a ring is as far round as the raise has gone. A `telegraph` arriving while stalled is taken, as the server's state, but its caster's cast does not start, and a circle that struck during the stall does not flare on return. A minion crumbling, or told to crumble while stalled, is gone on the first frame after the stall, with no light, and so is a body fading. A one-shot clip started in the first 1.5 s of a hide may still finish, because the clips are the animation mixers', not the combat effects'. A fall still waiting for its blow starts on the first frame after the stall, since the stall dropped the blow.
- **Before login the world plays a reel.** `packages/web/src/splash/` stages the committed sectors with scripted dreamers, NPCs, and nightmares. The sectors are compiled into the bundle through `@somnio/core/fixtures/sectors/*`, so the reel needs no server. Its dreamers are of all four peoples, each in a fixed outfit of neutral pieces at the tiers their land drops. It plays a fixed run of 6–8 s shots joined by a dip to dark, and reduced motion holds the first shot with a still camera. A fixture edit can put a wall in a scripted path or move an edge into a framing, and `splash-reel.test.ts` fails on either. It requires every path to be legal and every outdoor framing to stay on ground. Each figure a shot is about must be on screen whole, its name plate included, and clear of the card's column, which also covers the wordmark because the wordmark is narrower than the card. In a shot that follows a subject, every figure must be framed that way too once it stands. On a window too narrow to hold those figures beside the card, the camera of a followed shot pulls back, up to the scene's widest scale. A 50% veil dims the world. The wordmark sits in a band that ends above the tallest pre-login card, so it never moves between cards. A shot that stages a new space, or places a dreamer in the space already staged, holds the dip until the scene is settled, its dreamers dressed included, for at most 3 s (`SETTLE_LIMIT_SECONDS` in `director.ts`). The reel stops when a session attaches, and the scene's held swap carries its last frame into the game.
- **The pre-login screens give way when the player's own body is placed**, a little after `enterSpace`. Only then do the veil and the wordmark go and the HUD appear, and a later join never brings the splash back. When the session ends the HUD hides and closes its chat and windows. Until then a failed login says why on the login card, and a silent resume's retry says so under the wordmark.
- **A cold entry is covered until the player is dressed.** Each `enterSpace`, a login, a resume, or a door, arms the loading cover (`packages/web/src/ui/loadingCover.ts`). It stands from the first frame after the player's own body is placed until that body is drawn in all they wear, so the player never sees themselves undressed. That is `WorldRenderSurface.ownBodyDressed`: every worn piece loaded or failed, and its last join run. A placeholder body counts as dressed. For the cover alone, so does a body that wears nothing before its first bake, though `isSettled` still waits for that bake. It is an opaque layer over the canvas and the HUD. The HUD, the open windows, and the chat keep their state under it but are made `inert`, and the cover takes the focus, so Enter in a chat field focused before it sends nothing. World input is held: `ConnectionController.loadingCovered` closes `GameplayPredictor.gateIsOpen` and the shell's presses, and a press held as it rises lets go. Apart from the cover, while the models load under the loading notice (`WorldScene.warming`), the world's keys wait and the HUD stays hidden, since a resume can place the player, as a placeholder, before the models are warm. After 3 s it says the gear is still loading and offers Try Again, which loads each of the player's pieces still loading again under a URL of its own (`WorldScene.retryOwnOutfit`, `ModelAssets.retryWear`), since three joins a request for a URL already in flight. Only the body being dressed lowers it, never a timer: each frame `ConnectionController.settleLoadingCover` latches the cover down once `ownBodyDressed` holds, with no frame from the server needed. Lowered, it stays down for the rest of the space, so a piece put on in play pops in as anyone's does. Escape under it opens the game menu (see "One target"). As it lowers, the cover hands the keyboard back to what had it only while nothing stands over the world, neither an overlay nor a blocking notice such as the card asking an upright phone to turn (`AppShell.nothingOverWorld`), so a chat field focused before it does not take Enter behind either. An entry whose pieces are all loaded shows no cover, since the body is dressed before the space is revealed (see "Dressing is spread over frames").
- **Nothing reaches the world behind what covers it.** A layer that stands over the world, an overlay, the loading cover, or a blocking notice such as the loading notice or the turn-sideways card, holds every way input gets through at once: the window's world keys, presses on the canvas, Tab into the HUD (made `inert` or hidden), and the keyboard handed back as it goes. `AppShell.nothingOverWorld` is the one check for an overlay or a notice, read by the cover's hand-back and the world keys' gate alike. A new layer over the world joins that check rather than gating one path at a time.
- **A login lands on the character card**, one of the pre-login screens, with the reel still playing behind it. New Dreamer opens a form for a name and a people, and Delete asks first in an overlay of its own. The card locks its buttons from a request until its answer, so a double click sends one request. Every card request is answered, so unlike a carrier's panel the lock needs no fallback timeout. Log Out on the card revokes a remembered session and returns to the login card, as Leave Game does from the world. A resume of an account with a dreamer played goes straight into the world. The player's own name comes from their own `entity` frame.
- **`window.somnio`** is a read-only debug surface (dev always, production via `?debug=1`). It reports positions in metres in the space's coordinates, each entity's `condition`, an elite's or a boss's `rank` and an elite's `trait`, and the player's own state. `telegraphs()` lists the circles under way in view, each with its seconds left. `screenPoint(entityId)` is where on the page an entity is drawn, a fallen body where it lies, for a click aimed at it, and `groundScreenPoint(x, z)` is where a point of the space is drawn on the ground, for a tap aimed there. `loot()` lists the drops lying for the player, each with what it is (`kind`, an item's `baseId`, `tier`, `rarity`, and a set piece's `line`, or a trophy's `monsterKind`) and where its name and its model are drawn. `fixtures()` lists the fixtures of the held sectors with where each is drawn, `quests()` gives the quest log and the day's bounties as the last `quests` frame said, and `questMarkers()` each carrier in view that shows a marker, with where it is drawn. `questTracker()` gives the quests the tracker lists, in its order, at most three, and whether it shows, its list shows, and a finger's list is folded. `inventory()` gives each bagged item its place, and `characterBody()` where the Character window draws the body and how far it is turned. `frameStats()` gives what the last few seconds of frames cost (see "Frame budget"). They are reads, not commands: a recipe drives the client with real pointer events at those points. The `/somnio-web` skill lists every call and covers driving the client with `agent-browser`.

## Frame budget

New visual work is held to what a frame costs on the reference. That is the owner's Mac (Apple M5 Pro) running headless Chrome through `agent-browser`, with a 1440×900 window at device scale 2 (a 2880×1800 canvas, 4× MSAA), in Edaria Square, a meadow, and the crypt in a fight. Each line below sits a little above what the client cost there when the budget was set (1.2 to 1.4 ms of script, about 300 draw calls, 2.1 ms of GPU outdoors), so it leaves room for a little more but not for a new cost. A change that would cross a line says so, with its figures, before it lands.

- **Script:** p95 at most 2 ms a frame, from `window.somnio.frameStats()` (`scriptMs`, and `partsMs` for where it goes).
- **Draw calls:** at most 350 a frame, the sun's shadow pass included, which draws about two thirds of them. `frameStats()` gives the window's mean (`drawCalls`) and its worst frame (`drawCallsMax`). A dressed dreamer costs about two (see "A dressed body is one mesh").
- **GPU:** at most 2.5 ms a frame outdoors and 1 ms in a room, timed as the `/somnio-web` skill's "Frame time" recipe does, against the code before the change in alternating bursts.
- **Hitches:** no frame spends more than 6 ms of script on loading work, such as a sector arriving, a model first seen, or a fight starting. A field and a scatter go to a worker, and every program the world draws compiles in `WorldScene.prewarm`, so new work that draws something new adds its program there. A crossing's work that no render could show yet is held to a 1 ms slice, while what the view could show still builds in the frame it comes within reach (see "A sector entering in play is drawn over frames"). The one exception is a new space's reveal (see "The ground is painted, not textured"), which the held swap hides.

Absolute times hold only on an idle reference machine: the same frame measured 2.5 times slower while simulators ran beside it. The reference cannot show what only a real display does, such as the compositor drawing the HUD over the canvas, a 120 Hz refresh (8.3 ms a frame), or a larger window. Neither can it show a phone's GPU. Nobody measures those, so the lines above keep headroom for them. The world is drawn at a device scale of at most 2 (`MAX_PIXEL_RATIO` in `worldScene.ts`), so a phone at 3 shades no more pixels per CSS pixel than the reference does.

On a device no profiler reaches, such as a phone, `?debug=1` and `window.somnio.frameStats()` read the same figures. `scriptMs` counts only the frame's own callback. An `intervalMs` above the refresh with little script in it therefore means the frame waits on something else. That is either the GPU or work between frames, such as a message's handling, and a profile tells the two apart.

## Web map editor

The map editor is a second Vite entry point (`packages/web/editor.html` + `packages/web/src/editor/**`) that authors `.somnio-sector` files — a development tool, not a shipped surface:

- **Dev-only by construction.** `editor.html` is deliberately never added to `build.rollupOptions.input`, so `vite build`'s default single input (`index.html`) keeps it out of `dist/` and therefore out of the image. `npm run build` machine-enforces this: `packages/web/scripts/assertEditorExcluded.mjs` runs after `vite build`, inside the image build too, and asserts `dist/editor.html` is absent and no editor marker (`__editor/sectors`, `somnioEditor`, `somnio-editor-root`) reaches `dist/bundle` or `dist/index.html`.
- **File I/O is a dev-server middleware** (`packages/web/vite.editorFs.ts`): a `configureServer`-only plugin serving `/__editor/sectors` (GET list, GET/PUT per percent-encoded stem, no DELETE), inert unless `SOMNIO_EDITOR_SECTORS_DIR` is set (the `editor` npm script sets it, defaulting to the repo-root `sectors/` staging directory; a dev server with `SOMNIO_SECTORS_DIR` pointed there plays what is being authored, and finished sectors are copied into `packages/core/fixtures/sectors`, the world the server image ships and the splash reel stages), loopback-only and same-origin-gated regardless of `--host`, path-contained against the realpath'd root, and atomic on write.
- **The sector codec** (`packages/core/src/sectorFile.ts`) is pinned byte-for-byte by the committed fixtures, each of which reads and writes back identical, so an authored save never rewrites unrelated bytes of a sector the server loads. The writer runs its output through the reader before returning it, so the editor cannot save a file the server would refuse.
- **The overlay shows what blocks.** The authoring overlay draws each placement's registry colliders along with walk surfaces, ledges, door triggers, and arrival points. A door and a fixture are the record kinds without a tool. A door is added from its placement's inspector at one of the model's anchors, and a fixture from the same inspector's Service picker, one to a placement, which None removes. Renaming a placement re-points its doors and fixtures, deleting it deletes them, and copying it carries them along under new ids.
- **The document is judged as `buildWorld` would judge it.** Every other sector in the directory is loaded on open, and `documentIssues` (`packages/web/src/editor/surroundings.ts`) runs `buildWorld` over all of them. The overlay marks each reported record in red, and `window.somnioEditor.issues()` lists them. What the rules need of named sectors (the inn's spawn, and every carrier, sector, and place a quest of `packages/core/data/quests.json` names, such as the Healers' trial's `NorthWood` and the Mystics' trial's three hidden places, each a point inside `WestMeadow`, `AutumnWood`, or `NorthMeadow`) is checked by the server alone, in `ruleSectorIssues`.
- **Neighbours are drawn read-only.** For an outdoor document the outdoor sectors touching it are drawn at their origins, so roads, walls, and tree lines can meet across a border.
- **Record labels are DOM elements** over the canvas, so `agent-browser snapshot` sees them.
- **English-only.** The editor renders literal English and never imports `@/i18n`, keeping `RENDERED_KEYS` and the catalog tests untouched.
- **It shares the client's chrome.** The editor loads `packages/web/src/ui/chrome.css` and builds its corner panels with the `packages/web/src/ui/dom.ts` helpers (`floating`, `floatingStack`, the panel and button builders). A change to either reaches the editor too, so check it there as well as in the game.
- **A selection is a value.** The shell's selection list, the document's undo and redo stacks (a rename's `from` and `to`), and the inspector hold the same `{kind, id}` objects. Nothing writes to one: a rename replaces it (`followRename`), since a written id would change what an undo restores.
- **No field commits on focus change when the commit reshapes the rows.** A press moves focus before its click, so a commit on blur that adds, removes, or rebuilds rows detaches the pressed control and the click is lost. A blur may commit only an edit to a value that keeps the panel's shape. An Id is such a value. Every field finds its record through the record the inspector holds for its rows, and a rename puts the renamed record there, so the rows refresh in place. A control that adds or removes rows, such as an NPC's New step box, writes only on its button or Enter, and stands outside the step rows that adding or removing a step rebuilds.
- The `/somnio-editor` skill covers serving and driving the editor with `agent-browser` (`window.somnioEditor` is its debug surface).

## Web asset pack

The browser reads glTF. `somnio-assets` carries `Web/Models/*.glb`, published by its `Pipeline/build-web-models.sh`, and `Web/Branding/` (the favicon, home-screen icon, and wordmark), written by its `Branding/scripts/export_web.py`. The panel textures and the HUD's icons live in that repo's root `UI/`. `Scripts/bundle-web-assets.sh` composes the served root from the three:

```
SOMNIO_ASSET_SOURCE=/path/to/somnio-assets \
SOMNIO_WEB_ASSET_DEST=packages/web/dist/assets \
  Scripts/bundle-web-assets.sh
```

The destination differs by consumer, and getting it wrong fails silently. `packages/web/dist/assets` is for the image build, where nginx serves `dist/`; the **dev server needs `packages/web/public/assets`**. Vite serves `packages/web/public` and `packages/web/`, never `dist/`, so a pack written to `dist` leaves every model and texture missing, answered by the SPA fallback's HTML, with a placeholder world and no error. `packages/web/public/assets` is gitignored and excluded from the Docker context, so a populated dev pack never leaks into an image.

`UI/` and `Web/Branding/` are required, because neither the chrome nor the brand has a fallback. Models only warn. The brand is served at `/assets/Branding/`. The script and CI's pack check both check its four files by name, and every `UI/` file the client loads (`UI_FILES` in the script), because a directory check passes a partial export. A missing icon would draw its control blank. `packages/web/test/ui-pack.test.ts` holds that list to the `/assets/UI/` URLs under `packages/web/src` and to CI's check. An icon added to the HUD therefore needs its file in `somnio-assets` first: that repo is pushed before the somnio commit that names the file, or CI's pack check fails.

`UI/Items/<baseId>.png` holds one picture per base item, which the HUD draws an item as (`itemIcons.ts`). For armour and jewellery it is the tier-1 design's, and `UI/Items/<baseId>-t<n>.png` holds the design's at tiers 2 to 5 (`WARDROBE_ICONS`). `UI/Items/<baseId>-<role>-t<n>.png` holds a role line's design, a set piece's. The client names only those at `SET_TIERS` (`WARDROBE_LINE_ICONS`). The pipeline's `render_item_icons.py` renders each from the item's hand model, else its ground model, in three-quarter view at 128 px on a transparent ground, and gates the set. A new base item therefore needs its model registered and its picture rendered in `somnio-assets`, one per tier for armour and jewellery and one per role at each of `SET_TIERS`, and the picture named in `UI_FILES` and CI's check, before the client names it.

The script additionally verifies **external resource sidecars**, both `buffers[]` and `images[]`, which is the whole surface glTF 2.0 declares external files on. Today's pack is entirely self-contained binary GLB, so the check finds nothing. It exists because a JSON glTF can point at a sibling `.bin` or `.png`, which three.js resolves relative to the model URL, so a pipeline change that started emitting one would serve a 404 for the model's geometry or its texture.

The served layout is `/assets/...` for the pack and `/bundle/...` for hashed build output (`build.assetsDir: 'bundle'`). They must not share a directory — the client references the pack by absolute URL.

Prop models (the registry's `objectModels` stems, empty `expectedClips`) are **placement-normalized before export**: local origin at the ground-footprint center, long horizontal axis along X. The runtime adds no per-object scale and puts each clone's origin at its placement's `x`/`z`, turned by `yaw`. Collision never measures a loaded model: it comes from the registry's `footprint` and `colliders`, so an un-normalized prop draws shifted or mis-sized against what it blocks. The pipeline's footprint gate holds each written model's ground bounds to its registry `footprint`. The pipeline's sizing modes and authoring conventions live in that repo's `CLAUDE.md`.

Hand models (the registry's `handModels` stems) are not placement-normalized. Each is exported in the frame of the KayKit `handslot` bone it is held on, its grip at the origin, and the scene hangs a clone at identity under that bone of the dreamer's model: `handslotr` for the main hand and `handslotl` for the off hand, as `GLTFLoader` names `handslot.r` and `handslot.l`. The characters themselves export unarmed. The pipeline's hand-prop gate holds each written hand model static and at its grip.

Ground models (the registry's `groundModels` stems) are what a drop lies on the ground as, one for every item that can drop. They are placement-normalized like props, but lying: the lowest point on the ground plane, the ground bounds centred on the origin, and the size a dreamer holds or wears the item. The scene puts a clone's origin at the drop's point, turned by the drop's own yaw, and never measures it to place or size it. It measures the loaded model only to stand the drop's name under its bounds and to press the grass by its reach. A weapon's, a shield's, and a focus's come from the same KayKit piece as their hand model, laid flat. Armour and jewellery lie as their design at the tier they rolled at, a set piece as its line's, the `wardrobe` row's `ground` (`ModelAssets.ground(baseId, tier, line?)`). Every tier's and every line's ground model prewarms with the drops. The pipeline's ground-item gate holds each written ground model static, on the ground, centred, and no bigger than a held item.

Worn pieces (the stems of the registry's `wardrobe` rows' `wear`) are skinned to the KayKit skeleton the peoples' bodies share, each with its own inverse binds, which `preparePiece` maps onto the wearer's skeleton by joint name (see "A dressed body is one mesh"). Each loads the first time a dreamer wears it, and a missing one only warns, leaving the base clothes it would cover showing.

Trophy models (the registry's `trophyModels` stems) are what a trophy lies on the ground as, by the kind of nightmare that left it, normalized and laid as a ground model is and held by the same ground-item gate. A kind the table does not list has its trophy drawn as its name alone. They compile in `WorldScene.prewarm` with the ground models.

## Hosting

`packages/web/Dockerfile` builds `ghcr.io/tobihagemann/somnio-web` from a **repository-root** context (the workspace symlinks resolve through the root `node_modules`, and the asset pack is at `assets/`). It requires `--build-arg BUILD_VERSION` like the server image, and greps the bundle for the marked stamp `somnio-web <version>` to prove the version was injected — see `packages/web/src/buildInfo.ts` for why the stamp interpolates the define directly rather than reusing the exported constant.

There are no releases, version numbers, tags, or changelog. The `publish` job in `ci.yml` builds both images from every commit on `main` that passes the other four jobs and pushes them as `ghcr.io/tobihagemann/somnio-server` and `somnio-web`, each tagged `sha-<short>` and `latest`. `BUILD_VERSION` is that short sha, so the admin `version` verb and the `somnio-web <version>` stamp name the exact commit a container runs. The deployment runs `latest` for both images and redeploys whenever any service in its stack changes, so any green commit on `main` can go live at any moment: a change that breaks the wire must bump `helloVersion` in the same commit (registry geometry counts, see "Wire protocol"), and the committed sector fixtures are the live world.

The static image does **not** proxy `/ws`; whatever fronts it performs the split (the `proxy` service in `docker-compose.example.yml` locally, Traefik in production), which is what lets the client's origin-relative `wss://<host>/ws` resolve with no dev-only branch.
